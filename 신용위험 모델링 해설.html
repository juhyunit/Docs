03타깃(정답) 정의 — 무엇을 "부도"라고 부를 것인가 (셀 9~12)

코드가 하는 일

이게 모델링 전체에서 가장 중요한 결정입니다. 코드는 세 가지 정의를 준비해뒀습니다.

↔ 밀기
정의 부도(1)로 볼 상태 특징
original 16일 이상 연체 + 상각 + 부도 원본과 동일 (기본값)
basel90 31일 이상 연체 + 상각 + 부도 국제 규제(Basel) 기준에 가까움
matured_only 상각 + 부도만, 진행중 건은 아예 제외 편향 없음, 데이터는 절반으로

그리고 타깃의 방향을 뒤집었습니다. 원본은 "정상=1"이었는데, 이걸 "부도=1"로 바꿨습니다.

왜? model.predict_proba(X)[:, 1]은 "1일 확률"을 줍니다. 정상=1이면 이게 상환 확률이 되고, PD(부도확률)를 얻으려면 매번 1 - p를 해야 합니다. 그러면 SHAP 부호도 뒤집히고, 비용 계산도 뒤집히고, 실수하기 딱 좋습니다. 부도=1로 두면 모델 출력이 곧바로 PD가 됩니다.

여기서 두 가지를 짚어야 합니다.

(1) "Does not meet the credit policy" 2,749건이 조용히 버려졌습니다. 코드가 경고를 띄우고 지웠는데, 사실 이건 초창기(2007~2008) 렌딩클럽이 자기 심사 기준을 통과 못 한 대출을 실험적으로 내준 것입니다. 상태 뒤에 붙은 "Fully Paid / Charged Off"를 보고 매핑했어야 맞습니다. 2,749건은 226만 건 중 0.12%라 결과에 영향은 없지만, "경고가 떴는데 그냥 넘어갔다"는 건 실무에서 위험한 습관입니다.

(2) 부도율 12.72%, 불균형비 1:6.9. 100명 중 13명이 부도. 이 정도면 "심한 불균형"까진 아니지만, 정확도(Accuracy)를 쓰면 안 되는 수준입니다. 전부 "정상"이라고 찍어도 정확도 87.3%가 나오니까요.

실무 해설

타깃 정의를 바꾸면 모델이 통째로 바뀝니다. 이건 기술 문제가 아니라 정책 문제입니다.

실무에서 이 결정은 데이터 사이언티스트가 혼자 하지 않습니다. 리스크 관리 부서, 상품 부서, 준법 부서가 같이 정합니다. 왜냐하면:

  • 부도 기준을 느슨하게(16일 연체) 잡으면 → 부도 건수가 늘고 → 모델이 보수적이 되고 → 승인율이 떨어져 매출이 줄어듭니다.
  • 엄격하게(90일 연체) 잡으면 → 승인율은 오르지만 → 실제 손실을 과소평가합니다.

국제 기준(Basel III)은 90일 연체 또는 "상환 가능성 없음" 판단을 부도로 봅니다. 한국 금융권도 이 기준을 따릅니다. 그래서 original 정의(16일)는 사실 학습용으로는 괜찮지만 실무 기준으로는 너무 공격적입니다.

실습 과제: TARGET_DEF = "basel90"으로 바꿔서 다시 돌려보세요. 부도율이 얼마나 떨어지고 AUC가 어떻게 변하는지 보면, 타깃 정의의 힘을 체감할 수 있습니다.

04결측치 처리 (셀 13~15)

코드가 하는 일

MISSING_THRESHOLD = 51.0     # 51% 넘게 비어 있으면 컬럼 삭제

KEEP_NA_FLAG = ["mths_since_last_delinq", ...]   # 단, 이건 "비었다"는 사실을 기록

    df[f"{c}_isna"] = df[c].isna().astype(int)

핵심 아이디어: 결측에는 두 종류가 있습니다.

  • 그냥 없는 것 (url이 전부 비어 있음) → 지우면 됨
  • 없다는 게 정보인 것 (mths_since_last_delinq = "마지막 연체 이후 개월 수") → 이게 비어 있으면 연체를 한 번도 안 했다는 뜻! 오히려 좋은 신호입니다.

두 번째 경우를 그냥 지우거나 평균으로 채우면 중요한 정보를 버리는 것입니다. 그래서 _isna 플래그 컬럼을 따로 만들어 남겼습니다.

실무 해설

"51%"라는 숫자에는 이론적 근거가 없습니다. 관행일 뿐입니다.

실무에서는 임계값을 기계적으로 정하지 않고 컬럼별로 판단합니다. 90% 비어 있어도 그 10%가 결정적이면 살립니다. 대신 이때는 반드시 "결측 = 별도 구간" 으로 처리해서 WoE를 계산합니다.

그리고 실무에서 진짜 중요한 질문은 이겁니다: "운영 시점에도 이 컬럼이 채워질까?"

학습 데이터에서는 80% 채워져 있는데 실제 신규 신청 시스템에서는 20%만 들어오는 필드가 흔합니다. (예: 배치로 나중에 붙는 외부 신용정보) 이런 걸 모르고 모델에 넣으면 배포하자마자 성능이 폭락합니다. 이걸 실무에서 "학습-서빙 불일치(training-serving skew)" 라고 부르고, ML 시스템 장애 원인 1위입니다.

  • 대출 실행 시점 이후에 생기는 값은 전부 제외

또 하나 중요한 것 — addr_state(거주 주)가 들어가 있습니다. 이건 공정성(fairness) 리스크입니다. 미국에서 우편번호/주는 인종과 강하게 상관되어 있어서, 이걸 쓰면 레드라이닝(redlining, 특정 지역 차별) 으로 간주될 수 있습니다. 미국 ECOA/공정주택법, 한국 신용정보법 모두 이런 대리변수(proxy variable)를 문제 삼습니다. 실무라면 반드시 제거하거나, 사용 시 공정성 검증을 통과해야 합니다.

09Out-of-Time 분할 — 시간을 기준으로 나누기 (셀 30~32)

코드가 하는 일

X_oot = X_full[is_oot]     # 2018: 최종 시험용 (딱 한 번만 사용)

X_train, X_valid = train_test_split(X_dev, test_size=0.2, stratify=y_dev)

3단 분할입니다.

↔ 밀기
셋 용도 비유
Train 모델이 학습 교과서
Valid 모델 고르기, 임계값 정하기, 보정하기 모의고사
OOT Test 최종 성능 확인, 딱 한 번만 수능

왜 Valid와 Test를 나누나? Valid를 보고 "이 모델이 낫네" 하고 고르는 순간, Valid는 이미 오염됩니다. 여러 모델 중 Valid에서 제일 잘한 걸 골랐으니, 그 성능에는 운(運)이 섞여 있습니다. 그래서 한 번도 안 본 데이터(OOT) 가 따로 필요합니다.

실제로 나온 결과

Train 15.46% vs OOT 2.99%. 7번 섹션에서 본 만기 편향이 그대로 드러났습니다. 이 차이가 뒤에 나오는 모든 지표를 왜곡합니다.

실무 해설

랜덤 분할 vs 시간 분할, 왜 이렇게 중요한가

랜덤으로 나누면 2015년 데이터가 Train에도, Test에도 들어갑니다. 그런데:

  • 같은 시기의 경기 상황, 금리 환경, 렌딩클럽의 심사 정책이 양쪽에 똑같이 들어갑니다.
  • 모델이 "2015년 특유의 패턴"을 외워서 Test에서 잘 맞힙니다.
  • 실제 배포는 항상 "미래"에 하는데, 미래는 학습 데이터에 없습니다.

그래서 시계열 성격이 있는 데이터는 무조건 시간 분할입니다. 이건 신용 모델뿐 아니라 수요예측, 이탈예측, 주가예측 전부 마찬가지입니다.

더 나아가면: 실무에서는 Walk-Forward Validation을 씁니다.

학습[2014-2015] → 검증[2016]
학습[2014-2016] → 검증[2017]
학습[2014-2017] → 검증[2018]

이렇게 여러 번 반복해서 "이 모델이 어느 시기에나 안정적인가" 를 봅니다. 한 번의 OOT는 그 해가 특이했을 수도 있으니까요.

여러분 결과의 문제: OOT의 부도율이 2.99%라서, 이건 "2018년 고객이 좋았다"가 아니라 "2018년 데이터가 아직 안 익었다" 입니다. 제대로 하려면 OOT를 2016년으로 잡고 2017~2018은 아예 빼는 게 맞습니다. (2016년산은 관측 시점 기준 2~3년 지나서 충분히 익음)

10WoE와 IV — 신용 모델의 전통 무기 (셀 33~38)

코드가 하는 일

WoE (Weight of Evidence, 증거 가중치) 는 "이 구간은 평균보다 얼마나 안전한가" 를 하나의 숫자로 바꾸는 방법입니다.

WoE = ln ( 이 구간의 정상 비중이 구간의 부도 비중 )
  • WoE 양수(+) = 평균보다 안전
  • WoE 음수(−) = 평균보다 위험
  • WoE 0 = 평균과 같음

IV (Information Value, 정보값) 는 그 변수 전체의 예측력을 하나의 숫자로 요약한 것입니다.

↔ 밀기
IV 판정
< 0.02 예측력 없음 → 버림
0.02 ~ 0.1 약함
0.1 ~ 0.3 보통
0.3 ~ 0.5 강함
> 0.5 의심 (누수 아닌지 확인)

개선한 점 3가지:

  1. Laplace 스무딩 — 원본은 1e-6을 더해서 0 나눗셈을 피했는데, 그러면 표본이 적은 구간에서 WoE가 ±13 같은 미친 값이 나옵니다. 각 구간에 0.5건씩 더하는 방식으로 바꿨습니다.
  2. Train에서만 계산 — 원본은 전체 데이터로 계산해서 검증 데이터 정보가 새어 들어갔습니다.
  3. 최소 구간 크기 강제 — 2% 미만 구간은 자동으로 SMALL로 통합.

중복 변수 문제

term_months(0.0777)와 term_36_months(0.0777) — IV가 소수점까지 똑같습니다. 당연합니다. 36개월/60개월 두 값밖에 없으니 두 변수는 정보가 100% 동일합니다. 이런 완전 중복 변수는 선형 모델의 계수를 망가뜨립니다. (뒤 17번 섹션에서 실제로 확인됩니다) 하나는 지워야 합니다.

왜 트리 모델 시대에도 WoE를 배우나

LightGBM이 더 좋은데 왜 굳이? 세 가지 이유입니다.

  1. 규제 대응 — 감독당국은 여전히 "WoE + 로지스틱 회귀" 스코어카드를 가장 신뢰합니다. 설명이 되고, 검증이 되고, 30년간 검증된 방법이기 때문입니다.
  2. 탐색 도구 — IV 표를 보면 모델을 만들기 전에 어떤 변수가 쓸모 있는지 5분 만에 압니다.
  3. 결측/이상치 자동 처리 — WoE는 결측을 별도 구간으로 다루므로 대치가 필요 없습니다.

실무 관행: 탐색은 WoE/IV로, 챔피언 모델은 GBM으로, 규제 제출용은 스코어카드로 — 이렇게 병행 운영하는 곳이 많습니다.

11전처리 파이프라인 — 누수를 구조적으로 막기 (셀 39~40)

코드가 하는 일

num_pipe = Pipeline([("imputer", SimpleImputer(strategy="median"))])
cat_pipe = Pipeline([
    ("imputer", SimpleImputer(strategy="most_frequent")),
    ("ohe", OneHotEncoder(handle_unknown="infrequent_if_exist",
                          min_frequency=0.01, sparse_output=False)),
])
preprocessor = ColumnTransformer([("num", num_pipe, num_cols),
                                  ("cat", cat_pipe, cat_cols)])

preprocessor.fit(X_train)     # ⭐ 학습 데이터에서만 규칙을 배움
Xtr = to_df(X_train)          # 배운 규칙을 적용
Xva = to_df(X_valid)          # 같은 규칙 적용 (다시 배우지 않음)
Xte = to_df(X_oot)            # 같은 규칙 적용

원본은 이렇게 했습니다 잘못된 방식

imputer = SimpleImputer(strategy='mean')
X_imputed = imputer.fit_transform(df_final)     # 전체 데이터로 평균 계산
X_train, X_test = train_test_split(...)          # 그 다음에 나눔

무엇이 문제인가? 평균을 계산할 때 테스트 데이터의 값이 이미 들어갔습니다. 시험 문제를 채점 기준 만들 때 참고한 셈입니다. 미세하지만 성능이 부풀려집니다.

Pipeline의 진짜 가치는 편의성이 아니라 "실수를 구조적으로 불가능하게 만드는 것"입니다. fit은 train에만, transform은 모두에 — 이 규칙이 코드 구조에 박혀 있어서 어길 수가 없습니다.

handle_unknown="infrequent_if_exist" 는 중요한 안전장치입니다. OOT 데이터에 학습 때 못 본 새로운 범주(예: 새로운 주(州) 코드)가 나와도 에러 없이 "희귀 범주"로 처리합니다. 이게 없으면 운영 중에 크래시가 납니다.

중앙값 vs 평균: 연소득 같은 변수는 극단값(1억 달러 오입력) 때문에 평균이 왜곡됩니다. 중앙값은 이런 이상치에 흔들리지 않습니다.

실제로 나온 결과

변환 후 피처 수: 139

범주형 8개가 원핫 인코딩되면서 57개 컬럼으로 늘어났습니다. (82 + 57 = 139)

실무 해설

파이프라인은 "저장 가능한 단위"라는 게 핵심입니다.

실무에서 모델을 배포할 때, 모델 파일만 저장하면 안 됩니다. 전처리 규칙도 같이 저장해야 합니다.

  • 중앙값이 얼마였는지
  • 원핫 인코딩 컬럼 순서가 어땠는지
  • 어떤 범주를 "희귀"로 분류했는지

이게 안 맞으면 에러도 안 나고 조용히 틀린 예측을 합니다. 가장 무서운 종류의 버그입니다. joblib.dump({"preprocessor": ..., "model": ...}) 로 통째로 저장하는 이유입니다.

더 나아가면: 실무에서는 Feature Store를 씁니다. 학습 파이프라인과 서빙 파이프라인이 같은 코드로 피처를 만들도록 강제하는 시스템입니다. (Feast, Tecton, 또는 사내 구축) 학습-서빙 불일치를 원천 차단하는 방법입니다.

실무 해설

학습 시간이 실무에서 왜 중요한가

개발 속도 = 실험 횟수입니다. 한 번 돌리는 데 23분이면 하루에 20번밖에 실험 못 합니다. 11초면 하루에 수천 번 할 수 있습니다. 이 차이가 모델 품질의 차이로 직결됩니다.

그래서 실무 워크플로는 이렇습니다:

  1. 탐색 단계 — LightGBM으로 빠르게 100번 실험 (피처 조합, 하이퍼파라미터)
  2. 확정 단계 — 최종 후보만 다른 모델들과 비교
  3. 제출 단계 — 규제 제출용 로지스틱 회귀는 마지막에 한 번만

LightGBM이 11초 만에 끝났다는 것의 의미

n_estimators=2000으로 설정했는데 11초에 끝났다는 건, 조기 종료(early stopping)가 아주 일찍 발동했다는 뜻입니다. 나무를 200개도 안 만들고 멈춘 겁니다.

그리고 실제로 LightGBM은 AUC 0.6912로 꼴찌를 했습니다. 이건 LightGBM이 나쁜 게 아니라 학습이 덜 됐다는 신호입니다. 뒤에 SHAP 섹션에서 이게 심각한 결과를 낳습니다.

개선 방법:

lgb.LGBMClassifier(
    n_estimators=3000,
    learning_rate=0.02,          # 더 천천히
    min_child_samples=200,
    scale_pos_weight=(1-부도율)/부도율,   # is_unbalance 대신 명시적으로
)
# 조기 종료를 300라운드로 늘리고, eval_metric을 "average_precision"으로

이 결과의 심각한 문제

정상 고객 188,228명을 거절했습니다. 전체 정상 고객 298,029명 중 63%입니다.

실무에서 이런 모델을 배포하면:

  • 신청자의 67%가 거절됩니다 (승인율 33%)
  • 매출이 3분의 1로 폭락합니다
  • 영업 부서가 폭동을 일으킵니다

비용 비율 10:1이 너무 공격적이었습니다. 실제 계산은 이렇게 해야 합니다:

FN 비용 = 대출금액 × EAD × LGD
        = 1,500만원 × 0.9 × 0.6 = 810만원

FP 비용 = 대출금액 × 순이자마진 × 기간 × (1 − 부도율)
        = 1,500만원 × 0.04 × 3년 × 0.85 = 153만원

실제 비율 = 810 / 153 ≈ 5.3 : 1

게다가 거절된 고객의 평생가치(CLV) 도 계산에 넣어야 합니다. 거절당한 고객은 다시 안 옵니다. 다른 상품(카드, 예금)의 잠재 수익도 함께 잃습니다.

실무 해설

보정이 왜 돈 문제인가

은행의 기대손실(Expected Loss) 공식:

EL  =  PD × LGD × EAD
  • PD = 부도확률 (우리 모델)
  • LGD = 부도시 손실률 (담보 회수 후 못 받는 비율, 보통 40~70%)
  • EAD = 부도시 익스포저 (부도 시점의 잔액)

이 EL이 결정하는 것들:

↔ 밀기
용도 PD가 틀리면
대손충당금 회계 오류 → 재무제표 재작성, 감사 지적
위험조정 금리 금리를 잘못 매김 → 손실 또는 경쟁력 상실
규제자본(RWA) 자본을 잘못 쌓음 → 감독 제재
IFRS 9 / K-IFRS 기대신용손실 계산 오류 → 회계 부정 소지

순위만 맞고 확률이 틀린 모델은 대출 승인은 가능하지만 회계는 불가능합니다. 그래서 보정은 선택이 아니라 필수입니다.

여기서 배울 것 — "임계값과 보정은 모집단에 종속된다"

모델 파라미터(가중치)는 그대로여도, 임계값과 보정 곡선은 모집단이 바뀌면 다시 맞춰야 합니다.

실무에서 모집단이 바뀌는 상황:

  • 마케팅 채널 변경 (오프라인 지점 → 앱 유입)
  • 상품 변경 (금리 인하로 우량 고객 유입)
  • 경기 변동 (코로나, 금리 급등)
  • 경쟁사 정책 변경 (경쟁사가 조이면 우리 쪽으로 나쁜 고객이 몰림)

대응 방법:

  1. 주기적 재보정(recalibration) — 모델은 그대로, 보정만 월/분기 단위로 갱신
  2. 기저율 보정(prior correction) — 새 모집단의 부도율을 알면 수식으로 보정 가능
pnew = p · πnewπoldp · πnewπold + (1−p) · 1−πnew1−πold
  1. 승인율 기준 임계값 — "PD 0.35 이상 거절"이 아니라 "상위 위험 20% 거절" 로 운영 이러면 모집단이 바뀌어도 승인율이 안정적입니다. 실무에서 아주 흔한 방식입니다.

17SHAP — 모델이 왜 그렇게 판단했는지 (셀 56~72)

SHAP의 원리 — 축구팀 비유

축구팀이 3골을 넣었습니다. 각 선수가 몇 골씩 기여했나?

  • 손흥민 없이 뛰면 평균 1.2골 → 손흥민 기여 1.8골
  • 김민재 없이 뛰면 평균 2.4골 → 김민재 기여 0.6골
  • ...

이걸 가능한 모든 조합에 대해 계산해서 평균 낸 것이 Shapley value입니다. 1953년 노벨경제학상 수상자 로이드 섀플리가 만든 개념이고, 2017년에 머신러닝에 적용됐습니다.

f(x) = φ0 + ∑j=1..M φj
  • φ₀ = 기준값 (아무것도 모를 때의 평균 예측)
  • φⱼ = 변수 j의 기여도

기여도를 다 더하면 정확히 예측값이 됩니다. 이게 SHAP의 핵심 보장입니다.

19스코어카드 변환 — 확률을 점수로 (셀 77~79)

코드가 하는 일

BASE_SCORE, BASE_ODDS, PDO = 600, 50, 20
FACTOR = PDO / np.log(2)                      # = 28.85
OFFSET = BASE_SCORE - FACTOR * np.log(BASE_ODDS)   # = 487.1

def pd_to_score(p):
    good_bad_odds = (1 - p) / p
    return OFFSET + FACTOR * np.log(good_bad_odds)

왜 확률을 점수로 바꾸나?

  • "부도확률 8.3%" → 고객도 심사역도 감이 안 옴
  • "신용점수 620점" → 직관적, 다른 점수와 비교 가능

PDO(Points to Double the Odds) 가 핵심 개념입니다. "오즈가 2배 좋아질 때 몇 점을 더 줄 것인가" 입니다.

pi_old, pi_new = 0.1546, 0.0299     # Valid 부도율, OOT 부도율
odds_ratio = (pi_new / (1 - pi_new)) / (pi_old / (1 - pi_old))

B. 방법론의 한계

5. 심각 렌더 결정변수 사용 (grade, int_rate)

6. 주의 상관관계 ≠ 인과관계

로지스틱 회귀 계수를 보면:

installment    +0.3042  (부도↑)
loan_amnt      -0.1595  (부도↓)   ← ??
term_months    +0.0787  (부도↑)
term_36_months -0.0787  (부도↓)   ← 완전 중복 변수

loan_amnt가 클수록 안전하다? 상식과 반대입니다. 이건 다중공선성(multicollinearity) 때문입니다. loan_amnt, installment, term은 수학적으로 거의 종속 관계라서, 모델이 이들 사이에 양수/음수를 임의로 배분합니다.

따라서 이 계수를 "대출금액이 클수록 안전하다"고 읽으면 안 됩니다. 개별 계수는 다른 변수를 고정했을 때의 효과일 뿐, 인과 효과가 아닙니다.

C. 공정성·규제의 한계

9. 심각 공정성 검증 미실시

addr_state(거주 주)가 모델에 들어가 있습니다. 미국에서 지역 정보는 인종의 강력한 대리변수이고, 이걸 대출 심사에 쓰면 레드라이닝(redlining) 으로 간주될 수 있습니다.

검증해야 할 것:

  • 보호속성(인종/성별/연령)별 승인율 격차
  • Disparate Impact Ratio — 소수집단 승인율 / 다수집단 승인율 ≥ 0.8 (80% 룰)
  • Equal Opportunity — 집단별 TPR 격차
  • 대리변수 탐지 — 보호속성을 다른 변수로 예측할 수 있는가

마지막으로 — 이 프로젝트에서 가장 값진 것

"AUC 0.99가 나왔을 때 기뻐하지 않고 의심하는 습관" 입니다.

원본 Kaggle 노트북은 AUC 0.99를 얻고 "Neural Network가 아주 좋다"고 결론지었습니다. 여러분의 개선판은 AUC 0.73을 얻고, 그 숫자마저도 왜 못 믿는지를 스스로 증명했습니다.

더 낮은 숫자를 얻고 더 많은 문제를 발견한 것이 진전입니다.

실무에서 데이터 사이언티스트의 가치는 모델을 잘 만드는 것보다 "이 모델을 믿어도 되는가"를 판단하는 능력에서 나옵니다. 그 판단은 항상 세 가지 질문으로 시작합니다.

  1. 이 변수는 언제 생기는가? (누수)
  2. 이 정답은 다 익었는가? (만기 편향)
  3. 이 변수는 우리가 만들 수 있는 건가, 남이 준 건가? (순환 논리)

이 노트북은 세 질문을 전부 던졌고, 세 번 다 문제를 찾아냈습니다. 그게 이 프로젝트의 진짜 결과물입니다.
