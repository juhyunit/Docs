이 자료를 읽는 법

이 자료는 지금까지의 대화에서 나온 질문을 모두 모아, 한 번 읽으면 스킬을 다른 곳에서 더 찾아보지 않아도 되도록 정리한 것입니다. 개념 설명마다 우리가 만든 hwp-skill-kit의 실제 파일과 실제 실행 결과를 붙였습니다.

헷갈렸던 질문과 짧은 답

대화에서 여러 번 되돌아온 질문들입니다. 짧은 답을 먼저 보고, 자세한 설명은 오른쪽 장에서 읽으세요.

질문짧은 답장
이건 kordoc으로 만든 것 아닌가? 스킬과 kordoc은 무엇이 다른가?맞습니다. HWPX 파일은 kordoc이 만듭니다. 스킬은 kordoc을 언제, 어떤 원고로, 어떤 검사를 거쳐 부를지 적은 업무 매뉴얼입니다.1·7
runner, work 같은 형태가 대중적인 표준 포맷인가?아닙니다. 표준은 SKILL.md의 형식뿐이고, runner와 work는 우리가 붙인 이름입니다.1·4
스킬은 결국 LLM이 보기 편한 가이드를 프롬프트로 만든 것인가?셋 중 하나만 맞습니다. 스킬은 지시문(프롬프트) + 실행되는 도구(스크립트) + 필요할 때만 꺼내 보이는 규칙입니다.4
LLM은 스킬 폴더를 어떻게 가져와서 참고하나?모델은 파일을 열지 못합니다. 모델이 "이 파일을 읽어 달라"고 글로 요청하면, 실행기가 대신 읽어서 글로 넣어 줍니다.3·5
한 요청에 LLM을 여러 번 부르나? 컨텍스트는 계속 늘어나나?그렇습니다. 우리 시험에서는 요청 하나에 모델을 9번 불렀고, 모델에게 보낸 글이 2,014자에서 12,271자로 늘었습니다.2
"컨텍스트 전체를 동시에 놓고 어텐션 연산을 한다"는 게 무슨 뜻인가?모델이 글을 앞에서부터 한 글자씩 기억하며 읽는 게 아니라, 각 토큰이 자기 앞의 모든 토큰을 한꺼번에 비교한다는 뜻입니다.2
로컬 PC의 Qwen에 붙이다가 FileNotFoundError가 났다.파이썬이 파일을 찾는 기준 폴더와 압축을 푼 위치가 달라서입니다. 절대경로로 지정하면 해결됩니다.9
사내 로컬 LLM에서도 스킬이 맞는 방식인가? 스킬이 수십 개가 되면?작은 모델이면 모델의 판단을 줄이고 코드가 순서를 정하는 편이 안정적입니다. 참고 문서가 수십 개면 검색 방식과 섞어 씁니다.10
개인이 만든 kordoc을 믿어도 되나? 나도 엔진을 만들 수 있나?HWPX는 공개된 국가표준이라 개인도 만들 수 있고, 여러분도 만들 수 있습니다. 믿을지는 라이선스, 검증 방식, 교체 가능성으로 판단합니다.7

읽는 순서

  • 직접 연결해 볼 때는 8장과 9장을 옆에 띄워 두세요. 코드 오른쪽 위 복사 버튼으로 가져갈 수 있습니다.
  • 사내 도입을 판단할 때는 10장을 먼저 보고 11·12장으로 넘어가세요.

표시 규칙

  • 각 장은 당신이 물었던 것(대화 속 실제 질문)과 한 줄 정리로 시작하고, 스스로 확인 문제로 끝납니다. 문제를 누르면 답이 열립니다.
  • 형광펜은 그 장에서 꼭 기억할 문장입니다.
  • 누가 만든 것인지 헷갈리지 않도록 다음 표시를 붙입니다. 표준 여러 제품이 함께 따르는 공개 규격, 우리 것 이 kit에서 우리가 정하거나 만든 것, 오픈소스 남이 만들어 공개한 라이브러리, 국가표준 한국 국가표준.

큰 그림: 다섯 개의 층

당신이 물었던 것
  • "이건 kordoc으로 한 거 아닌가?"
  • "skill.md도 있고 runner도 있고 보고서 작성 룰 같은 md 파일도 있는데 이게 kordoc과 다른 점은?"
  • "work, runner 등 이런 형태가 대중적인 포맷이 된 건가?"
한 줄 정리

HWP 문서 하나가 만들어지기까지 다섯 층이 일을 나눠 맡습니다. 모델은 글만 쓰고, 실행기가 손발이 되고, 스킬은 매뉴얼이고, kordoc은 파일을 찍는 기계이고, HWPX 표준은 그 기계가 따르는 설계도입니다.

가.비유: 전화로만 일하는 전문가

비유

문서 작성 전문가를 전화로만 쓸 수 있다고 해 봅시다. 전문가는 말을 듣고 말을 할 수만 있고, 우리 사무실의 서류를 직접 만질 수 없습니다.

그래서 사무실에 직원이 한 명 있습니다. 직원은 전문가가 "업무 매뉴얼 3장을 읽어 줘"라고 하면 읽어 주고, "이 원고를 검사기에 넣어 봐"라고 하면 넣어 보고 결과를 불러 줍니다. 단, 사무실 규칙상 허락된 일만 합니다.

사무실 책장에는 업무 매뉴얼 바인더가 있고, 그 안에 작성 규칙과 검사기가 들어 있습니다. 구석에는 한글 문서를 찍어 내는 문서 제작 기계가 있고, 그 기계는 나라에서 정한 문서 규격서대로 파일을 만듭니다.

전문가 = 모델, 직원 = 실행기, 바인더 = 스킬, 기계 = kordoc, 규격서 = HWPX 표준입니다.

나.다섯 층 한눈에 보기

각 층이 무엇을 알고 무엇을 모르는지 정리하면 다음과 같습니다.

층아는 것모르는 것
① 모델한국어, 문장 쓰는 법, 도구 호출 형식내 PC에 무슨 파일이 있는지, 우리 은행 규칙, HWPX 내부 구조
② 실행기스킬 폴더 위치, 허용된 동작(읽기·쓰기·실행)기안문이 무엇인지, HWPX 구조
③ 스킬기안문 작성 순서, 사내 표기 규칙, 어떤 스크립트를 언제 쓸지HWPX 내부 구조(엔진에 맡김)
④ kordocHWPX의 zip 구성, 문단·표·글꼴 XML은행 업무 규칙, 결재선이 맞는지
⑤ HWPX규격 그 자체. 한글 프로그램과 kordoc이 모두 이 규격을 따르므로 서로 파일을 주고받을 수 있습니다.

다.무엇이 표준이고 무엇이 우리가 정한 이름인가

"runner, work가 표준 포맷이 되었나"라는 질문의 답이 이 표입니다. 표준으로 정해진 것은 SKILL.md의 형식 하나뿐이고, 스킬을 읽고 실행하는 프로그램은 제품마다 각자 만듭니다.

이름정체누가 정했나
SKILL.md 형식머리말(name, description)과 본문표준 agentskills.io 명세
scripts/ references/ assets/스킬 폴더 안의 권장 하위 폴더 이름표준 명세의 권장 사항(필수 아님)
.agents/skills/여러 제품이 스킬을 찾는 공용 위치표준 관례. 명세는 위치를 강제하지 않음. Claude Code는 .claude/skills/를 읽음
runner/, work/실행기 코드 폴더, 모델이 파일을 쓰는 폴더우리 것 아무 이름이나 써도 됨
discover.mjs · tools.mjs · agent.mjs우리 실행기우리 것 구현 가이드를 참고해 직접 작성
activate_skill 같은 도구 이름모델에게 준 도구우리 것 구현 가이드의 예시 이름을 따름
kordocHWPX를 만드는 라이브러리오픈소스 개인 개발자, MIT 라이선스
HWPX한글 문서의 개방형 파일 형식국가표준 KS X 6101

라."이건 kordoc으로 한 거 아닌가?"

맞습니다. HWPX 파일을 실제로 만드는 코드는 우리 스킬 안에 없습니다. 생성 스크립트 make_hwpx.mjs가 kordoc 함수를 한 줄로 부를 뿐입니다.

scripts/make_hwpx.mjs 중 실제로 파일을 만드는 줄
const bytes = await markdownToHwpx(md, { gongmun, warnings })   // kordoc이 HWPX를 만든다

그러면 우리가 만든 것은 무엇일까요? 그 한 줄의 앞과 뒤입니다.

  • 앞: 무엇을 쓸지(사내 규칙 문서), 틀린 표기가 없는지(검수 스크립트: kordoc의 공문서 표기 검사기에 사내 규칙 검사를 더함), 결재선을 지어내지 않았는지(자리표시자가 남으면 생성 거부)
  • 뒤: 만든 파일이 깨지지 않았는지, 꼭 들어가야 할 문구가 들어갔는지(검증 스크립트: kordoc으로 다시 읽어 확인)
  • 전체: 이 순서를 모델이 지키도록 적은 절차(SKILL.md)와, 모델 대신 실제로 실행해 주는 프로그램(runner/)

마.한 층씩 빼 보면 역할이 보인다

빼는 층무슨 일이 생기나
모델사람이 원고를 직접 쓰고 스크립트를 돌리면 됩니다. 스크립트는 모델 없이도 돌아갑니다.
실행기모델이 "스크립트를 실행해 달라"고 써도 아무 일도 일어나지 않습니다. 화면에 그 글자만 남습니다.
스킬모델은 우리 은행 규칙을 모른 채 아는 만큼만 씁니다. 검수도 검증도 없습니다.
kordoc잘 쓴 마크다운 원고까지만 나옵니다. .hwpx 파일은 만들지 못합니다.
HWPX 표준엔진이 따를 설계도가 없어 한글 프로그램이 열 수 있는 파일을 만들 방법이 없습니다.
스스로 확인
Q1. runner/ 폴더 이름을 engine-room/으로 바꾸면 스킬 표준을 어기는 것인가?

아닙니다. 실행기의 폴더 이름과 구조는 표준의 범위 밖입니다. 다만 agent.mjs 안에서 다른 파일을 불러오는 경로가 바뀌지 않도록 폴더째 옮기면 됩니다.

Q2. 모델을 Qwen에서 GPT로 바꾸면 어느 층을 고쳐야 하나?

실행기가 모델에 접속하는 설정만 바꿉니다(.env의 LLM_BASE_URL, LLM_MODEL, 필요하면 LLM_API_KEY). 스킬, 엔진, 포맷은 그대로입니다.

Q3. kordoc 대신 사내에서 만든 엔진을 쓰기로 했다. 어디를 고치나?

세 스크립트입니다. 생성은 make_hwpx.mjs의 render() 함수 하나만 바꾸면 되도록 모아 두었고, 검수(check_draft.mjs)와 검증(verify_hwpx.mjs)도 kordoc 기능을 쓰므로 함께 바꿉니다. 규칙 문서는 그대로 둡니다. 다만 새 엔진이 항목부호와 "끝."을 자동으로 붙이지 않는다면, 그 일을 엔진에 맡긴다고 적은 SKILL.md의 주의 문구도 고쳐야 합니다.

LLM의 기본 성질 네 가지

당신이 물었던 것
  • "한 번 LLM 수행한 결과, 조사한 결과 등을 합쳐서 최종 내용을 만드는 건가? LLM을 여러 번 수행시키는 게 맞아?"
  • "많은 과정을 수행할수록 프롬프트(컨텍스트)가 계속 늘어나는 구조인가? 얼마나 감당이 가능해? 한 번의 질문으로 들어가도 소화가 되나?"
  • "컨텍스트 전체를 동시에(병렬로) 놓고 어텐션 연산을 한다는 게 이해가 안 된다."
한 줄 정리

LLM은 기억이 없는 "글을 넣으면 이어질 글을 내는" 계산기입니다. 그래서 일이 여러 단계면 단계마다 지금까지의 대화 전체를 다시 넣어 부르고, 넣는 글은 단계마다 길어집니다.

가.모델은 "다음 글자 맞히기" 계산기다

모델이 하는 일은 하나입니다. 글을 받아서, 그 뒤에 이어질 가장 그럴듯한 조각을 하나 냅니다. 그 조각을 붙이고 다시 다음 조각을 내는 일을 반복해서 답 한 편이 됩니다. 이 조각을 토큰이라고 부릅니다. 한국어 한 글자가 몇 토큰인지는 모델마다 다릅니다.

여기서 두 가지가 따라 나옵니다.

  • 모델은 글만 다룹니다. 파일을 열거나 프로그램을 실행하는 기능이 없습니다. 이 빈자리를 메우는 방법이 3장의 도구 호출입니다.
  • 모델은 앞의 대화를 기억하지 않습니다. 아래에서 설명합니다.

나.기억이 없어서, 매번 처음부터 다시 보낸다

채팅 화면에서는 모델이 앞의 대화를 기억하는 것처럼 보입니다. 실제로는 화면 뒤의 프로그램이 호출할 때마다 지금까지의 대화 전체를 통째로 다시 보내기 때문입니다. Claude 공식 문서도 "시스템 프롬프트, 모든 메시지(도구 결과·문서 포함), 도구 정의가 요청마다 컨텍스트 창에 들어간다"고 설명합니다.

스킬로 기안문을 만드는 작업을 예로 들면, 모델을 부를 때마다 직전 단계의 결과가 뒤에 붙어서 다음 호출로 넘어갑니다.

같은 시험에서 기안문 한 건을 끝낼 때까지 모델을 9번 불렀고, 매번 보낸 글의 길이는 다음과 같았습니다.

그래서 "조사 결과와 첨부 파일을 합쳐 최종 내용을 만드는 별도의 단계"가 따로 있는 것이 아닙니다. 조사 결과, 파일 내용, 검수 결과가 모두 대화 기록에 글로 쌓여 있는 상태에서, 모델이 그다음 한 걸음을 정하는 일이 반복될 뿐입니다. 마지막에 "이제 됐다"고 판단한 호출의 출력이 최종 답입니다.

상용 API와 vLLM 같은 서버는 앞부분이 같은 요청이면 이전 계산을 재사용하는 캐시 기능을 두기도 합니다. 계산은 줄어도, 컨텍스트 창 한도에는 전체 길이가 그대로 들어갑니다.

다.컨텍스트 창: 한 번에 넣을 수 있는 양

Claude 공식 문서의 정의로는 컨텍스트 창은 "모델이 답을 만들 때 참고할 수 있는 모든 글(만들어지는 답 포함)"이며, 학습 데이터가 아니라 모델의 작업 기억입니다. 이 한도는 토큰 수로 셉니다.

대화에서 "지금 모델의 정확한 한도는 확인하지 못했다"고 답했는데, 공식 문서를 확인해 보니 Claude Sonnet 5와 Opus 5.5는 1,000,000 토큰입니다.

표에서 가장 중요한 줄은 Qwen과 Ollama입니다. 실제로 쓸 수 있는 한도는 모델 카드의 숫자가 아니라 모델을 띄운 서버의 설정이 정합니다. 262,144 토큰을 지원하는 모델도, GPU 메모리가 24GiB보다 작은 PC에서 Ollama를 기본값으로 띄우면 4,096 토큰까지만 씁니다. 위 시험의 마지막 호출(12,271자)은 Qwen 계열 어휘로 어림하면 약 5,800토큰이라 4,096을 넘습니다. Ollama는 OLLAMA_CONTEXT_LENGTH=64000 ollama serve처럼 서버를 띄울 때 한도를 올립니다. 한도를 올리면 GPU 메모리도 더 씁니다.

한도를 넘을 때의 동작은 서버마다 다릅니다. vLLM은 오류를 돌려줍니다. Ollama는 시스템 프롬프트와 가장 최근 메시지는 남기고, 그 사이의 오래된 메시지를 조용히 빼고 진행합니다. 처음 요청, 스킬 본문, 앞에서 읽은 규칙 파일이 오류 없이 빠질 수 있다는 뜻이고, 그러면 모델은 규칙을 잊은 채 계속 일합니다. 오류가 나는 쪽보다 이쪽이 더 알아차리기 어렵습니다.

라.한도 안이어도, 길면 흐려진다

  • 컨텍스트 부패(context rot). Claude 공식 문서는 "토큰 수가 늘수록 정확도와 기억력이 떨어진다"고 적고, 그래서 창이 얼마나 큰지만큼 무엇을 넣을지 고르는 일이 중요하다고 설명합니다.
  • 가운데에서 길을 잃음(lost in the middle). Liu 등의 연구(TACL, 2024)는 필요한 정보가 긴 입력의 처음이나 끝에 있을 때 모델이 가장 잘 쓰고, 가운데에 있으면 성능이 크게 떨어진다고 보고했습니다.
  • 느려지고 비싸집니다. 모델이 한 번에 처리하는 계산은 길이가 길수록 가파르게 늘고(아래 마), 에이전트 반복에서는 매번 전체 기록을 다시 보내므로 보낸 양이 누적됩니다. 위 시험의 9번 호출에서 보낸 글을 모두 합치면 76,967자로, 마지막 호출(12,271자)의 약 6.3배입니다. 토큰 단위로 요금을 매기는 API라면 이 누적량이 비용이 됩니다.

스킬이 "필요한 것만, 필요할 때" 꺼내 보이도록 설계된 이유가 여기에 있습니다(5장).

마.어텐션을 쉽게: 회의실에서 한 번에 둘러보기

비유

문장의 토큰들이 회의실에 들어온 순서대로 한 줄로 앉아 있다고 해 봅시다. 모델이 다음 말을 정하려면, 자기 앞에 앉은 모든 사람을 한 번에 둘러보고 "지금 이 말을 정하는 데 누구 말이 중요한가"를 점수로 매깁니다. 멀리 앉은 사람도 곧바로 봅니다. 아직 들어오지 않은 뒷사람(앞으로 쓸 말)은 볼 수 없습니다. 이 둘러보기가 어텐션입니다.

예전 방식(순환 신경망)은 옆 사람에게 귓속말로 요약을 넘기는 전달 게임과 비슷했습니다. 앞사람의 말을 전해 듣기만 하니, 멀리 있는 말일수록 흐려졌습니다.

"동시에(병렬로)"라는 말은 두 단계로 나눠 보면 정확해집니다.

단계하는 일병렬인가
읽기들어온 글 전체에 대해, 각 토큰이 자기 앞의 모든 토큰을 둘러보는 계산을 합니다.예. 모든 토큰의 계산을 한꺼번에 합니다. "한 글자씩 순서대로 읽으며 기억해 둔다"가 아닙니다.
쓰기답을 한 토큰씩 만듭니다. 새 토큰을 하나 만들 때마다 앞의 모든 토큰을 다시 둘러봅니다.아니요. 답은 한 토큰씩 차례로 나옵니다.

순서가 뒤섞이지 않는 이유는, 각 토큰에 "몇 번째 자리인지"라는 위치 정보가 함께 들어가기 때문입니다.

길수록 비싼 이유. 각 토큰이 자기 앞의 모든 토큰을 둘러보므로, 토큰이 N개면 비교하는 쌍이 대략 N×N÷2개입니다. 길이가 2배면 비교는 약 4배입니다.

토큰 수비교하는 쌍 (약 N×N÷2)
1,000약 500,000
10,000약 50,000,000
100,000약 5,000,000,000

실제 서버는 계산을 저장해 두었다 다시 쓰는 등의 최적화로 이보다 효율적으로 돌지만, 글이 길수록 비용이 가파르게 늘어난다는 방향은 같습니다.

스스로 확인
Q1. 모델에게 "아까 그 파일 다시 봐 줘"라고 하면, 모델이 파일을 기억하고 있어서 가능한 것인가?

아닙니다. 아까 읽은 파일 내용이 대화 기록에 글로 남아 있고, 이번 호출에도 그 기록 전체가 다시 실려 왔기 때문에 볼 수 있는 것입니다. 기록이 잘려 나가면 모델은 그 파일을 "잊습니다".

Q2. Qwen3-4B-Instruct-2507은 262,144 토큰을 지원한다. Ollama로 띄우면 바로 그만큼 쓸 수 있나?

아닙니다. GPU 메모리가 24GiB보다 작으면 Ollama 기본값은 4,096 토큰입니다. OLLAMA_CONTEXT_LENGTH로 올려야 하고, 올린 만큼 GPU 메모리가 더 필요합니다.

Q3. 컨텍스트 창 안에만 들어가면 모든 내용을 똑같이 잘 참고하나?

아닙니다. 길어질수록 정확도가 떨어지고(context rot), 가운데에 묻힌 정보는 덜 쓰는 경향이 있습니다(lost in the middle). 그래서 필요한 것만 넣는 설계가 중요합니다.

도구 호출: 손이 없는 모델이 일을 시키는 방법

당신이 물었던 것
  • "스킬 폴더들을 만들고 나서 나의 LLM 모델들은 그걸 참고할 때 어떤 방식으로 가져와서 참고하는거야?"
  • "pipeline(...) 이런 형태의 로컬 모델에서 내 스킬을 넣고 보고서 파일을 만들고 싶어."
한 줄 정리

모델은 "이 도구를 이 값으로 불러 달라"는 글을 쓸 뿐이고, 실제 실행은 모델 밖의 코드가 합니다. 실행 결과는 다시 글이 되어 다음 호출 때 모델에게 돌아갑니다.

가.모델은 도구를 직접 부르지 못한다

Hugging Face transformers 공식 문서는 이렇게 적고 있습니다. "모델은 실제로 도구를 스스로 호출할 수 없습니다. 도구 호출을 요청할 뿐이고, 그 호출을 처리해 결과를 대화 기록에 붙이는 것은 여러분의 일입니다."

1장의 비유로 말하면, 전화 속 전문가는 "검사기에 넣어 봐"라고 말만 할 수 있고, 실제로 넣는 것은 사무실 직원입니다. 모델이 스킬 폴더를 "참고한다"는 말은, 실행기가 대신 파일을 읽어 그 내용을 대화에 글로 넣어 준다는 뜻입니다.

나.도구 호출 한 바퀴

다.도구 설명서: 모델에게 무엇을 줄 수 있는지 알려 주기

모델은 도구가 있다는 것을 설명서를 보고 압니다. 설명서는 이름, 하는 일, 받는 값(인자)을 JSON 형식으로 적은 것입니다. 아래는 우리 파이썬 연결 코드(8장)가 모델에게 주는 스킬 켜기 도구입니다.

도구 설명서 예: activate_skill
{"type": "function",
 "function": {
   "name": "activate_skill",
   "description": "요청이 스킬 설명과 맞으면 그 스킬의 전체 지시문을 불러온다.",
   "parameters": {"type": "object",
                  "properties": {"name": {"type": "string", "enum": ["writing-hwp-documents"]}},
                  "required": ["name"]}}}

enum은 "이 값들 중에서만 고르라"는 뜻입니다. 스킬 이름을 목록으로 못 박아 두면 모델이 없는 스킬 이름을 지어내기 어렵습니다.

# 한글(HWPX) 사내 문서 작성

사용자의 메모·자료를 사내 규칙에 맞는 원고(마크다운)로 쓰고, 스크립트로 검수한 뒤 HWPX 파일로 만든다.
파일 생성과 검수는 반드시 아래 스크립트로 한다. HWPX 내부 XML을 직접 만들지 않는다.

## 작업 순서

아래 체크리스트를 답변에 복사해 두고, 단계를 마칠 때마다 표시한다.

```
- [ ] 1. 문서 종류 정하기 (기안문 / 보고서)
- [ ] 2. 규칙 파일 읽기
- [ ] 3. 빠진 정보 확인
- [ ] 4. 원고 작성
- [ ] 5. 검수 (오류 0개까지 수정)
- [ ] 6. HWPX 생성
- [ ] 7. 결과 검증 후 보고
```

**1. 문서 종류 정하기**
- 결재를 받아 무언가를 실시·집행·요청하는 문서 → 기안문 (`--type gian`)
- 현황이나 검토 결과를 윗선에 알리는 문서 → 보고서 (`--type report`)
- 어느 쪽인지 애매하면 사용자에게 한 번 묻는다.

**2. 규칙 파일 읽기** (필요한 파일만 읽는다)
- 항상 읽기: [references/house-style.md](references/house-style.md) — 사내 용어와 금지 표현
- 기안문이면: [references/gian-rules.md](references/gian-rules.md)
- 보고서면: [references/report-rules.md](references/report-rules.md)
- 날짜·금액·붙임 표기가 헷갈릴 때만: [references/notation-rules.md](references/notation-rules.md)

**3. 빠진 정보 확인**
- 기안문에는 제목, 수신, 결재선(기안자·검토자·결재권자의 직위와 성명)이 필요하다. 없으면 지어내지 말고 사용자에게 묻는다.
- 숫자·금액·날짜·문서번호는 사용자가 준 자료에 있는 값만 쓴다. 자료에 없으면 `(확인 필요)`라고 쓴다.

**4. 원고 작성**
- 골격을 복사해서 채운다: 기안문은 [assets/templates/gian.md](assets/templates/gian.md), 보고서는 [assets/templates/report.md](assets/templates/report.md)
- 원고는 작업 폴더에 저장한다 (예: `<작업폴더>/draft.md`).
- 기안문이면 두문·결문 정보를 `<작업폴더>/meta.json`에 따로 쓴다. 골격: [assets/templates/gian.meta.json](assets/templates/gian.meta.json)

**5. 검수** — 오류가 0개가 될 때까지 고치고 다시 실행한다.

```bash
node scripts/check_draft.mjs <작업폴더>/draft.md --type gian
```

출력은 JSON이다. `errors`가 1 이상이면 `findings`의 `suggest`대로 원고를 고친다. `warnings`는 문맥을 보고 판단한다.

**6. HWPX 생성**

```bash
node scripts/make_hwpx.mjs <작업폴더>/draft.md --type gian --meta <작업폴더>/meta.json -o <작업폴더>/<파일명>.hwpx
```

- 보고서는 `--meta`를 빼도 된다.
- 파일명 규칙: `YYYYMMDD_종류_핵심어.hwpx` (예: `20260925_기안_디지털교육실시.hwpx`)

**7. 결과 검증 후 보고**

```bash
node scripts/verify_hwpx.mjs <작업폴더>/<파일명>.hwpx --expect "<제목>"
```

`"ok": true`를 확인한 뒤 사용자에게 알린다: 파일 경로, 남은 경고, `(확인 필요)`로 남긴 항목. 마지막에 "최종 검토와 결재 상신은 담당자가 직접 해야 합니다"라고 덧붙인다.

## 주의: 자주 틀리는 것

- 항목부호(`1.` `가.` `1)` 또는 `□` `○` `-`)는 직접 쓰지 않는다. 목록 들여쓰기(2칸)로 단계를 표현하면 엔진이 문서 종류에 맞는 부호를 붙인다.
- `끝.`은 원고에 쓰지 않는다. 기안문이면 엔진이 자동으로 붙인다.
- 날짜는 `2026. 9. 25.`, 시각은 `14:30`, 금액은 `금15,000,000원(금일천오백만원)` 형식이다.
- `붙임` 뒤에는 쌍점 없이 두 칸을 띄운다: `붙임  교육 일정표 1부.`
- 기안문 본문은 "~하고자 합니다", "~하시기 바랍니다"로, 보고서는 "~함", "~임" 같은 명사형으로 끝낸다.
- 고객 실명, 주민등록번호, 계좌번호는 원고에 넣지 않는다. 꼭 필요하면 `홍○○`, `***-**-****`처럼 가린다.
- 스크립트가 실패하면 오류 메시지의 안내를 따른다. 같은 명령을 그대로 반복하지 않는다.

검수 스크립트가 틀린 원고를 받았을 때 돌려주는 결과입니다. 스크립트는 사람이 아니라 모델이 읽는 프로그램이라, 어디가(line, match) 왜 틀렸고(message) 어떻게 고칠지(suggest)를 JSON으로 냅니다.

// 1단계 스킬 찾기 + 2단계 SKILL.md 읽기
//   스킬 폴더를 훑어서 SKILL.md가 있는 폴더를 찾고, 머리말(frontmatter)에서

// 외부 라이브러리 없이 Node 기본 기능만 쓴다(폐쇄망 반입을 쉽게 하기 위해).

import { readdirSync, readFileSync, existsSync } from "node:fs"
import { join, dirname } from "node:path"
import { homedir } from "node:os"

// 먼저 읽은 것을 나중에 읽은 것이 덮어쓴다. 표준 관례대로 "프로젝트 스킬이 사용자 스킬보다 우선"이 되도록
// 사용자 폴더를 먼저, 프로젝트 폴더를 나중에 둔다. 사내 공용 스킬 폴더가 있으면 맨 앞에 추가한다.
export function skillRoots(projectDir) {
  return [
    join(homedir(), ".agents", "skills"), // 사용자 단위 (모든 프로젝트 공용)
    join(projectDir, ".agents", "skills"), // 프로젝트 단위 (다른 도구와 같은 위치 규칙)
  ]
}

// 간이 YAML 파서. SKILL.md 머리말에 쓰이는 형태만 지원한다:
//   key: value / key: "value" / key: > 또는 | 여러 줄 / key: 다음 줄부터 들여쓴 하위 항목(metadata)
function parseFrontmatter(text) {
  const out = {}
  const lines = text.split(/\r?\n/)
  for (let i = 0; i < lines.length; i++) {
    const m = lines[i].match(/^([A-Za-z0-9_-]+):\s*(.*)$/)
    if (!m) continue
    const [, key, rawValue] = m
    const value = rawValue.trim()
    if (value === ">" || value === "|" || value === ">-" || value === "|-") {
      const block = []
      while (i + 1 < lines.length && /^\s+\S/.test(lines[i + 1])) block.push(lines[++i].trim())
      out[key] = value.startsWith(">") ? block.join(" ") : block.join("\n")
    } else if (value === "") {
      const map = {}
      while (i + 1 < lines.length && /^\s+\S/.test(lines[i + 1])) {
        const sub = lines[++i].trim().match(/^([A-Za-z0-9_-]+):\s*(.*)$/)
        if (sub) map[sub[1]] = unquote(sub[2].trim())
      }
      out[key] = map
    } else {
      out[key] = unquote(value)
    }
  }
  return out
}
const unquote = (v) => v.replace(/^"(.*)"$/, "$1").replace(/^'(.*)'$/, "$1")

export function parseSkillFile(path) {
  const raw = readFileSync(path, "utf8").replace(/^﻿/, "") // 윈도우 메모장이 붙이는 BOM 제거
  const m = raw.match(/^---\r?\n([\s\S]*?)\r?\n---\r?\n?([\s\S]*)$/)
  if (!m) return { error: "첫 줄이 ---로 시작하는 머리말(frontmatter)이 없음" }
  return { meta: parseFrontmatter(m[1]), body: m[2].trim() }
}

// 규칙이 조금 어긋나도 쓸 수 있으면 경고만 하고 불러온다(관대한 검증). description이 없으면 모델이
// 언제 써야 할지 알 수 없으므로 그 스킬만 건너뛴다.
export function discoverSkills(projectDir) {
  const skills = new Map()
  const warnings = []
  for (const root of skillRoots(projectDir)) {
    if (!existsSync(root)) continue
    for (const entry of readdirSync(root, { withFileTypes: true })) {
      if (!entry.isDirectory() || entry.name.startsWith(".") || entry.name === "node_modules") continue
      const location = join(root, entry.name, "SKILL.md")
      if (!existsSync(location)) continue
      const parsed = parseSkillFile(location)
      if (parsed.error) { warnings.push(`${location}: ${parsed.error} → 건너뜀`); continue }
      const { name, description } = parsed.meta
      if (!description) { warnings.push(`${location}: description이 없어 건너뜀`); continue }
      if (name && name !== entry.name) warnings.push(`${location}: name(${name})과 폴더 이름(${entry.name})이 다름`)
      const key = name || entry.name
      if (skills.has(key)) warnings.push(`스킬 이름 충돌 '${key}': ${location} 을(를) 사용`)
      skills.set(key, { name: key, description, location, dir: dirname(location) })
    }
  }
  return { skills, warnings }
}

const esc = (s) => String(s).replace(/&/g, "&amp;").replace(/</g, "&lt;").replace(/>/g, "&gt;")

// 모델에게 보여 줄 스킬 목록(1단계 공개). 스킬 하나당 50~100토큰 정도라 수십 개를 설치해도 부담이 작다.
export function catalogXml(skills) {
  const items = [...skills.values()].map((s) =>
    `  <skill>\n    <name>${esc(s.name)}</name>\n    <description>${esc(s.description)}</description>\n  </skill>`)
  return `<available_skills>\n${items.join("\n")}\n</available_skills>`
}

// 4단계 스킬 켜기 + 실행: 모델에게 주는 도구 네 가지
//   activate_skill  스킬 본문(SKILL.md)을 불러온다 (2단계 공개)
//   read_file       스킬 안의 참고 파일이나 작업 폴더의 파일을 읽는다 (3단계 공개)
//   write_file      작업 폴더에 원고·설정 파일을 쓴다
//   run_script      스킬의 scripts/ 안에 있는 스크립트만 실행한다
// 은행 환경에 맞게 "아무 명령이나 실행하는 셸"을 주지 않고, 허용 목록 방식으로 좁혔다.
// ─────────────────────────────────────────────────────────────
import { readFileSync, writeFileSync, mkdirSync, readdirSync, existsSync } from "node:fs"
import { join, resolve, relative, dirname, sep, extname, isAbsolute } from "node:path"
import { spawnSync } from "node:child_process"
import { parseSkillFile } from "./discover.mjs"

const MAX_OUTPUT = 8000 // 도구 결과가 너무 길면 모델 컨텍스트를 낭비한다. 잘라서 준다.
const SCRIPT_TIMEOUT_MS = 60_000 // 문서 생성은 보통 수 초 안에 끝난다. 1분이면 충분히 여유 있다.
const INTERPRETERS = { ".mjs": process.execPath, ".js": process.execPath, ".py": "python3" }

// target이 base 폴더 안(또는 base 자체)인지 확인한다. "../" 로 빠져나가는 경로를 막는다.
const inside = (base, target) => {
  const rel = relative(resolve(base), resolve(target))
  return rel === "" || (rel !== ".." && !rel.startsWith(".." + sep) && !isAbsolute(rel))
}
const clip = (s) => (s.length > MAX_OUTPUT ? s.slice(0, MAX_OUTPUT) + `\n…(${s.length - MAX_OUTPUT}자 생략)` : s)

// 따옴표를 지키며 명령 문자열을 인자 배열로 나눈다. 셸을 거치지 않으므로 ; && | 같은 기호가 명령으로 해석되지 않는다.
function splitArgs(command) {
  const out = []
  const re = /"([^"]*)"|'([^']*)'|(\S+)/g
  let m
  while ((m = re.exec(command))) out.push(m[1] ?? m[2] ?? m[3])
  return out
}

function listResources(dir) {
  const files = []
  const walk = (d) => {
    for (const e of readdirSync(d, { withFileTypes: true })) {
      if (e.name === "node_modules" || e.name.startsWith(".")) continue
      const p = join(d, e.name)
      if (e.isDirectory()) walk(p)
      else if (e.name !== "SKILL.md") files.push(relative(dir, p).split(sep).join("/"))
    }
  }
  walk(dir)
  return files.slice(0, 50)
}

export function createTools({ skills, workDir, log }) {
  const activated = new Set()
  const names = [...skills.keys()]

  // 스킬 본문을 구조화된 태그로 감싸서 준다. 모델이 스킬 지시문을 다른 대화와 구분할 수 있고,
  // 하네스는 나중에 컨텍스트를 줄일 때 이 부분을 지우지 않도록 식별할 수 있다.
  function activate(name) {
    const skill = skills.get(name)
    if (!skill) return `오류: '${name}' 스킬이 없습니다. 사용 가능: ${names.join(", ")}`
    if (activated.has(name)) return `'${name}' 스킬은 이미 불러와 있습니다. 앞의 지시를 계속 따르세요.`
    activated.add(name)
    const { body } = parseSkillFile(skill.location)
    const resources = listResources(skill.dir).map((f) => `  <file>${f}</file>`).join("\n")
    return `<skill_content name="${name}">\n${body}\n\n스킬 폴더: ${skill.dir}\n` +
      `이 스킬의 상대경로(scripts/, references/, assets/)는 스킬 폴더 기준이다. 파일을 읽을 때는 절대경로를 쓴다.\n` +
      `스크립트는 run_script 도구로 실행한다.\n<skill_resources>\n${resources}\n</skill_resources>\n</skill_content>`
  }

  function readFile(path) {
    const p = resolve(path)
    const allowed = [...skills.values()].some((s) => inside(s.dir, p)) || inside(workDir, p)
    if (!allowed) return `오류: 읽기가 허용되지 않은 경로입니다: ${p}\n스킬 폴더나 작업 폴더(${workDir}) 안의 파일만 읽을 수 있습니다.`
    if (!existsSync(p)) return `오류: 파일이 없습니다: ${p}`
    return clip(readFileSync(p, "utf8"))
  }

  function writeFile(path, content) {
    const p = resolve(workDir, path)
    if (!inside(workDir, p)) return `오류: 쓰기는 작업 폴더(${workDir}) 안에서만 할 수 있습니다.`
    mkdirSync(dirname(p), { recursive: true })
    writeFileSync(p, content)
    return `저장했습니다: ${p} (${Buffer.byteLength(content)}바이트)`
  }

  function runScript(skillName, command) {
    const skill = skills.get(skillName)
    if (!skill) return `오류: '${skillName}' 스킬이 없습니다.`
    if (!activated.has(skillName)) return `오류: 먼저 activate_skill로 '${skillName}' 스킬을 불러오세요.`
    if (/[;&|`$<>]/.test(command)) return "오류: 셸 기호(; & | ` $ < >)는 쓸 수 없습니다. 스크립트 명령 하나만 주세요."
    const argv = splitArgs(command)
    if (["node", "python3", "python"].includes(argv[0])) argv.shift() // "node scripts/x.mjs" 형태도 받아 준다
    const script = resolve(skill.dir, argv[0] ?? "")
    if (!inside(join(skill.dir, "scripts"), script) || !existsSync(script)) {
      return `오류: 이 스킬의 scripts/ 안에 있는 파일만 실행할 수 있습니다. 받은 값: ${argv[0]}\n` +
        `사용 가능: ${listResources(skill.dir).filter((f) => f.startsWith("scripts/")).join(", ")}`
    }
    const interpreter = INTERPRETERS[extname(script)]
    if (!interpreter) return `오류: 실행할 수 없는 파일 형식입니다: ${extname(script)}`
    // 스크립트에 넘기는 파일 경로도 작업 폴더 안으로 제한한다 (값을 받는 옵션 --type·--expect는 제외)
    const rest = argv.slice(1)
    for (let i = 0; i < rest.length; i++) {
      const a = rest[i]
      if (a.startsWith("-") || ["--type", "--expect"].includes(rest[i - 1])) continue
      if (!inside(workDir, resolve(skill.dir, a))) return `오류: 스크립트에 넘기는 파일은 작업 폴더(${workDir}) 안에 있어야 합니다. 받은 값: ${a}`
    }
    const r = spawnSync(interpreter, [script, ...argv.slice(1)], {
      cwd: skill.dir, encoding: "utf8", timeout: SCRIPT_TIMEOUT_MS, shell: false,
    })
    const result = { exit_code: r.status ?? -1, stdout: clip(r.stdout ?? ""), stderr: clip(r.stderr ?? "") }
    if (r.error) result.stderr += `\n실행 오류: ${r.error.message}`
    return JSON.stringify(result, null, 2)
  }

  // OpenAI 호환 API의 도구(function calling) 정의. 스킬 이름은 enum으로 제한해 모델이 없는 이름을 지어내지 못하게 한다.
  const definitions = [
    { type: "function", function: {
      name: "activate_skill",
      description: "작업이 스킬 설명과 맞으면 이 도구로 스킬의 전체 지시문을 불러온다. 지시문을 읽기 전에는 작업을 시작하지 않는다.",
      parameters: { type: "object", properties: { name: { type: "string", enum: names } }, required: ["name"] },
    } },
    { type: "function", function: {
      name: "read_file",
      description: "스킬 폴더나 작업 폴더 안의 텍스트 파일을 읽는다. 절대경로를 쓴다.",
      parameters: { type: "object", properties: { path: { type: "string" } }, required: ["path"] },
    } },
    { type: "function", function: {
      name: "write_file",
      description: "작업 폴더 안에 텍스트 파일을 저장한다(원고.md, meta.json 등). 같은 이름이면 덮어쓴다.",
      parameters: { type: "object", properties: { path: { type: "string" }, content: { type: "string" } }, required: ["path", "content"] },
    } },
    { type: "function", function: {
      name: "run_script",
      description: "불러온 스킬의 scripts/ 안 스크립트를 실행한다. command는 SKILL.md에 적힌 명령 그대로. 예: node scripts/check_draft.mjs /work/draft.md --type gian",
      parameters: { type: "object", properties: { skill: { type: "string", enum: names }, command: { type: "string" } }, required: ["skill", "command"] },
    } },
  ]

  async function call(name, args) {
    let result
    switch (name) {
      case "activate_skill": result = activate(args.name); break
      case "read_file": result = readFile(args.path); break
      case "write_file": result = writeFile(args.path, args.content ?? ""); break
      case "run_script": result = runScript(args.skill, args.command ?? ""); break
      default: result = `오류: 알 수 없는 도구 ${name}`
    }
    log({ event: "tool", name, args: name === "write_file" ? { path: args.path, chars: (args.content ?? "").length } : args, ok: !result.startsWith("오류") })
    return result
  }

  return { definitions, call, activate, activated }
}

  • 모델이 가장 익숙하게 쓰는 형식입니다. 제목은 #, 항목은 -, 들여쓰기는 두 칸. 틀릴 여지가 적습니다. 반대로 HWPX 속 XML을 모델이 직접 쓰게 하면 태그 하나만 틀려도 파일이 열리지 않습니다.
  • 내용과 서식을 나눕니다. 모델은 무엇을 쓸지만 정하고, 항목부호(1. 가. 1)), "끝." 표시, 두문·결문 표 같은 서식은 엔진이 규칙대로 입힙니다. 그래서 SKILL.md에 "항목부호와 끝.은 직접 쓰지 않는다"는 주의가 있습니다.

HWPX는 zip 파일입니다. 확장자를 .zip으로 바꿔 풀면 XML 파일 몇 개가 나옵니다. 아래는 우리 스킬이 만든 기안문 파일을 파이썬으로 열어 본 실제 결과입니다.

# HWPX 파일 속을 들여다보기: zip 안 파일 목록과 문단별 글자
import re, sys, zipfile

path = sys.argv[1] if len(sys.argv) > 1 else "20261015_기안_디지털교육실시.hwpx"
with zipfile.ZipFile(path) as z:
    for info in z.infolist():                                   # 1) 상자 안에 든 파일들
        print(f"{info.filename:28s} {info.file_size:7,d} 바이트")
    xml = z.read("Contents/section0.xml").decode("utf-8")       # 2) 본문 XML

for p in re.findall(r"<hp:p\b.*?</hp:p>", xml, re.S):          # 3) 문단(<hp:p>)마다
    parts = re.findall(r"<hp:t>(.*?)</hp:t>", p, re.S)          #    글자 칸(<hp:t>)을 모아

    text = re.sub(r"<[^>]+>", "", text).strip()                 #    나머지 태그는 지운다
    if text:
        print("문단:", text)

한컴의 공개 문서에는 사용 조건이 붙어 있습니다. 공개 문서를 참고해 만든 제품에는 "본 제품은 한컴의 HWP 문서 파일(.hwp) 공개 문서를 참고하여 개발하였습니다."라는 문구를 표시해야 하고, 문서 원본은 고치지 않은 채로만 배포할 수 있습니다. 사내 엔진을 직접 만든다면 이 조건을 법무·준법 부서와 함께 확인해야 합니다.

다.kordoc은 어떻게 만들어졌나

kordoc의 README와 NOTICE 파일에서 확인한 사실만 정리합니다.

항목내용
만든 사람GitHub 계정 chrisryugj. README 첫머리에 "7년 버틴 공무원이 만들었습니다"라고 적혀 있음
라이선스kordoc 자체는 MIT. 다만 NOTICE에 Apache-2.0 등 다른 라이선스의 코드가 함께 적혀 있음
하는 일HWP 3.x·5.x, HWPX, HWPML, PDF, XLS(X), DOCX를 마크다운으로 읽기, 공문서 생성, 문서 비교·서식 채우기. CLI와 MCP 서버로도 동작
rhwp와의 관계rhwp(개인 개발자 edwardkim의 Rust 오픈소스, MIT)의 HWP3 디코더, 배포용 HWP 복호화, 손상 파일 복구 알고리즘, 일부 조판 처리를 TypeScript로 옮겨 왔고, 기안문 서식 자산(templates/)도 rhwp에서 가져왔다고 밝힘. rhwp를 고쳐 만든 것이 아니라, 일부 알고리즘과 자산을 가져온 별개의 프로그램
생성 엔진의 근거README에 따르면 서울 정보소통광장 결재문서 629건을 전수 실측해 위계·글꼴·들여쓰기를 맞춤

정리하면 kordoc은 공개된 형식 문서, 커뮤니티가 쌓아 온 실물 분석 결과, 실제 공문서와의 대조라는 세 가지를 바탕으로 한 사람이 오래 다듬어 온 엔진입니다. 기업이 만들지 않았다는 점이 신기해 보이지만, 설계도가 공개되어 있으면 필요를 느낀 누구든 만들 수 있습니다. 워드의 .docx도 형식이 공개되어 있어 마이크로소프트 밖의 많은 도구가 읽고 씁니다.

라.개인이 만든 오픈소스를 은행에서 쓸 때의 판단 기준

"개인이 만들었으니 안 된다"도, "유명하니 괜찮다"도 판단 기준이 되기 어렵습니다. 다음을 봅니다.

기준kordoc + 우리 kit의 현재 상태
라이선스가 사내 사용·수정을 허락하나kordoc 자체는 MIT. 그러나 kordoc의 NOTICE에 Apache-2.0 코드가 있고, 함께 설치되는 의존성 128개에는 LGPL-3.0(이미지 처리 라이브러리 sharp의 libvips), MIT 또는 GPL-3.0 선택(jszip), Python-2.0(argparse) 등이 섞여 있음. 반입 전 법무·준법 부서의 라이선스 검토가 필요
검토한 버전과 쓰는 버전이 같은가package.json에 4.14.2 고정, lock 파일로 하위 의존성까지 고정
반입 전 코드를 검토할 수 있나소스 공개. 실행 중 인터넷에서 내려받는 명령(npx 등)은 쓰지 않도록 스크립트를 짬
개발이 멈추면 갈아탈 수 있나kordoc을 부르는 곳이 스크립트 세 개(생성은 make_hwpx.mjs의 render() 한 곳, 검수·검증은 각 스크립트)로 모여 있어, SKILL.md와 규칙 문서는 건드리지 않고 바꿀 수 있음
결과물을 우리가 직접 검증하나구조 검사·재판독은 자동. 한컴오피스로 직접 열어 보는 확인은 아직 못 함

다른 선택지도 있습니다. 사내 PC에 한/글이 설치되어 있다면, 윈도우에서 한/글 프로그램 자체를 코드로 조작하는 방식(한/글 오토메이션, 파이썬 라이브러리 pyhwpx 등)으로 문서를 만들 수 있습니다. 결과가 한/글과 완전히 같다는 장점이 있지만, 한/글이 설치된 윈도우 PC가 필요하고 서버에서 여러 사람이 동시에 쓰기는 어렵습니다. 사내 조건에 맞춰 비교해 볼 만합니다.

마.엔진을 직접 만든다면: 여섯 단계

가능합니다. HWPX는 공개된 XML 규격이라 "비밀을 알아내는" 일이 아니라 "규격대로 조립하는" 일입니다.

  1. 실물 파일을 뜯어보기. 한컴오피스로 간단한 문서를 만들어 저장하고, 위의 peek_hwpx.py처럼 열어 봅니다. 공개 문서가 말하는 것과 실제 저장되는 것을 나란히 봅니다.
  2. 공개 문서로 태그의 뜻을 확인하기. KS X 6101(OWPML)과 한컴 다운로드 센터의 문서, 한컴테크 블로그의 HWPX 구조 설명을 참고합니다.
  3. 고정 부분과 바뀌는 부분 나누기. mimetype, container.xml, header.xml(사내 서식을 한 번 정해 두면)은 거의 그대로 두고, 바뀌는 것은 section0.xml의 문단과 표입니다. 엔진의 핵심은 "원고 → section0.xml" 변환기입니다.
  4. 규칙대로 다시 묶기. 실물 파일처럼 mimetype을 맨 앞에 압축 없이 넣는 등 패키지 규칙을 따릅니다. 규칙에서 어긋나면 한컴 프로그램이 파일을 열지 못할 수 있습니다.
  5. 한컴오피스로 직접 열어 보기. 규격대로 만들었다고 한컴 프로그램이 항상 똑같이 보여 주는 것은 아닙니다. kordoc이 실제 결재문서 수백 건과 대조한 이유입니다.
  6. 범위를 조금씩 넓히기. 제목과 문단 → 표 → 글자 모양 → 결재란 → 그림 → 머리말·꼬리말 순서로 늘려 갑니다.

대화 초반에 실제로 이 과정을 따라 최소 버전(hwpx-lite, 약 400줄)을 만들어 kordoc의 파서로 다시 읽어 검증해 보았습니다. 제목과 문단 정도만 다루는 수준이었고, 표·결재란·정밀한 공문서 서식은 빠져 있었습니다.

목표현실적인 규모
제목과 문단만 되는 최소 버전며칠. 원리 이해에는 충분
표·결재란까지 사내 기안문을 믿고 맡길 수준몇 주에서 몇 달. 실물 문서 대조와 한컴오피스 확인이 대부분의 시간을 차지

판단. 원리를 몸으로 익히려면 최소 버전을 한 번 만들어 보는 것이 좋습니다. 실무 엔진은 이미 수백 건으로 맞춰 온 kordoc을 쓰되, 엔진을 부르는 곳을 스크립트 안에 가두어 두고 라이선스 검토와 사내 검증을 거치는 편이 시간 대비 효율적입니다. kordoc의 개발이 멈추거나 사내 요구가 달라지면 그때 자체 엔진으로 그 자리들을 바꾸면 됩니다.

스스로 확인
Q1. HWPX 안에서 "이 문단은 굵은 글씨"라는 정보는 section0.xml에 직접 적혀 있나?

번호만 적혀 있습니다(charPrIDRef). 굵기, 크기 같은 실제 모양은 header.xml에 그 번호로 정의되어 있습니다.

Q2. kordoc은 rhwp를 고쳐서 만든 프로그램인가?

아닙니다. 별개의 TypeScript 프로그램이고, rhwp의 일부 알고리즘(HWP3 디코더, 배포용 문서 복호화, 손상 파일 복구)을 옮겨 왔다고 밝히고 있습니다.

Q3. 사내에서 한컴 공개 문서를 참고해 엔진을 만들면 지켜야 할 조건은?

제품에 "본 제품은 한컴의 HWP 문서 파일(.hwp) 공개 문서를 참고하여 개발하였습니다." 문구를 표시하는 등 한컴이 밝힌 조건을 지켜야 합니다. 구체적인 적용은 법무 부서와 확인합니다.

  • 셸 기호 차단, scripts/ 밖 실행 차단, 켜지 않은 스킬의 스크립트 차단, 그리고 스크립트에 넘기는 파일 경로를 작업 폴더 안으로 제한하는 검사를 넣었습니다.
  • 모델이 윈도우식 경로(C:\…)를 써도 명령을 나눌 때 역슬래시가 사라지지 않도록 /로 바꿔 처리합니다.
  • 참고 파일은 <skill_resource>로 감싸 돌려줍니다. 대화를 줄일 때 스킬 자료를 알아보고 지키기 위해서입니다(10장 라).
skill_bridge.py
# ─────────────────────────────────────────────────────────────
# 스킬 연결 공통부 (파이썬판 discover.mjs + tools.mjs)
#   1) .agents/skills/ 에서 스킬을 찾아 이름·설명을 읽는다
#   2) 모델에게 보여 줄 시스템 프롬프트(스킬 목록)를 만든다
#   3) 모델이 부를 도구 4개를 "대신 실행"한다
# 어떤 모델(OpenAI, Qwen, Ollama …)을 붙이든 이 파일은 그대로 쓴다.
# ─────────────────────────────────────────────────────────────
import json
import re
import shlex
import subprocess
from pathlib import Path


class SkillBridge:
    def __init__(self, kit_dir):
        self.kit = Path(kit_dir).resolve()
        if not (self.kit / ".agents" / "skills").is_dir():
            raise FileNotFoundError(f"스킬 폴더가 없습니다: {self.kit / '.agents' / 'skills'}  (kit 경로를 확인하세요)")
        self.work = self.kit / "work"
        self.work.mkdir(exist_ok=True)
        self.skills = self._discover()
        self.activated = set()

    # ── 1) 찾기: SKILL.md 머리말에서 name·description만 읽는다 ──
    def _discover(self):
        skills = {}
        for d in sorted((self.kit / ".agents" / "skills").iterdir()):
            f = d / "SKILL.md"
            if not f.is_file():
                continue
            raw = f.read_text(encoding="utf-8-sig")          # -sig: 윈도우 메모장 BOM 제거
            m = re.match(r"^---\r?\n(.*?)\r?\n---\r?\n(.*)$", raw, re.S)
            if not m:
                continue
            meta = dict(re.findall(r"^([\w-]+):[ \t]*(\S.*)$", m.group(1), re.M))
            if "description" not in meta:
                continue
            skills[meta.get("name", d.name)] = {"dir": d, "description": meta["description"], "body": m.group(2).strip()}
        return skills

    # ── 2) 알리기: 시스템 프롬프트에 넣을 글 ──
    def system_prompt(self):
        items = "\n".join(
            f"  <skill>\n    <name>{n}</name>\n    <description>{s['description']}</description>\n  </skill>"
            for n, s in self.skills.items())
        return (
            "당신은 사내 업무를 돕는 도우미다. 한국어로 답한다.\n"
            f"작업 폴더: {self.work.as_posix()} (파일은 이 폴더에만 저장한다)\n"
            "사용자가 주지 않은 숫자·이름·날짜는 지어내지 않는다.\n\n"
            "아래 스킬 중 요청과 맞는 것이 있으면, 작업을 시작하기 전에 activate_skill 도구로 불러와 지시를 따른다.\n"
            f"<available_skills>\n{items}\n</available_skills>")

    # ── 도구 설명서 (Chat Completions·transformers 형식) ──
    def tool_specs(self):
        names = list(self.skills)
        obj = lambda props, req: {"type": "object", "properties": props, "required": req}
        s = {"type": "string"}
        return [
            {"type": "function", "function": {"name": "activate_skill", "description": "요청이 스킬 설명과 맞으면 그 스킬의 전체 지시문을 불러온다.",
                                              "parameters": obj({"name": {"type": "string", "enum": names}}, ["name"])}},
            {"type": "function", "function": {"name": "read_file", "description": "스킬 폴더나 작업 폴더 안의 텍스트 파일을 읽는다.",
                                              "parameters": obj({"path": s}, ["path"])}},
            {"type": "function", "function": {"name": "write_file", "description": "작업 폴더에 텍스트 파일을 저장한다.",
                                              "parameters": obj({"path": s, "content": s}, ["path", "content"])}},
            {"type": "function", "function": {"name": "run_script", "description": "불러온 스킬의 scripts/ 안 스크립트를 실행한다. command는 SKILL.md에 적힌 명령 그대로.",
                                              "parameters": obj({"skill": {"type": "string", "enum": names}, "command": s}, ["skill", "command"])}},
        ]

    # OpenAI Responses API는 한 겹 얕은 형식을 쓴다
    def tool_specs_responses(self):
        return [{"type": "function", **t["function"]} for t in self.tool_specs()]

    # ── 3) 실행: 모델 대신 파일을 읽고 쓰고 스크립트를 돌린다 ──
    def call(self, name, args):
        try:
            if name == "activate_skill":
                return self._activate(args["name"])
            if name == "read_file":
                return self._read(args["path"])
            if name == "write_file":
                return self._write(args["path"], args.get("content", ""))
            if name == "run_script":
                return self._run(args.get("skill", ""), args.get("command", ""))
            return f"오류: 알 수 없는 도구 {name}"
        except KeyError as e:
            return f"오류: 도구 인자 {e}가 빠졌습니다."

    def _activate(self, name):
        if name not in self.skills:
            return f"오류: '{name}' 스킬이 없습니다. 사용 가능: {', '.join(self.skills)}"
        if name in self.activated:
            return f"'{name}' 스킬은 이미 불러와 있습니다."
        self.activated.add(name)
        s = self.skills[name]
        return (f'<skill_content name="{name}">\n{s["body"]}\n\n'
                f"스킬 폴더: {s['dir'].as_posix()}\n"
                "참고 파일은 스킬 폴더 기준 절대경로로 read_file 한다. 스크립트는 run_script로 실행한다.\n</skill_content>")

    @staticmethod
    def _inside(base, target):
        try:
            Path(target).resolve().relative_to(Path(base).resolve())
            return True
        except ValueError:
            return False

    def _read(self, path):
        p = Path(path)
        if not p.is_absolute():                      # 상대경로면 켜 둔 스킬 폴더 기준으로 해석
            for n in self.activated:
                if (self.skills[n]["dir"] / p).exists():
                    p = self.skills[n]["dir"] / p
                    break
        allowed = self._inside(self.work, p) or any(self._inside(s["dir"], p) for s in self.skills.values())
        if not allowed:
            return f"오류: 읽을 수 없는 경로입니다: {p}"
        if not p.is_file():
            return f"오류: 파일이 없습니다: {p}"
        text = p.read_text(encoding="utf-8")[:8000]
        if self._inside(self.work, p):
            return text
        return f'<skill_resource path="{p.as_posix()}">\n{text}\n</skill_resource>'   # 스킬 자료는 표시해 둔다(줄이기에서 보호)

    def _write(self, path, content):
        p = (self.work / Path(path).name).resolve()   # 어떤 경로가 와도 작업 폴더 안으로
        p.write_text(content, encoding="utf-8")
        return f"저장했습니다: {p.as_posix()}"

    def _run(self, skill, command):
        if skill not in self.activated:
            return "오류: 먼저 activate_skill로 스킬을 불러오세요."
        if re.search(r"[;&|`$<>]", command):
            return "오류: 셸 기호(; & | ` $ < >)는 쓸 수 없습니다."
        argv = shlex.split(command.replace("\\", "/"))    # 윈도우 경로의 \ 를 / 로 (shlex가 \ 를 지우지 않게)
        if argv and argv[0] in ("node", "python", "python3"):
            argv = argv[1:]
        d = self.skills[skill]["dir"]
        script = (d / argv[0]).resolve() if argv else d
        if not self._inside(d / "scripts", script) or script.suffix != ".mjs" or not script.is_file():
            return "오류: 이 스킬의 scripts/ 안 .mjs 파일만 실행할 수 있습니다."
        # 스크립트에 넘기는 파일 경로도 작업 폴더 안으로 제한한다 (값을 받는 옵션 --type·--expect는 제외)
        args = argv[1:]
        for i, a in enumerate(args):
            if a.startswith("-") or (i > 0 and args[i - 1] in ("--type", "--expect")):
                continue
            target = Path(a) if Path(a).is_absolute() else d / a
            if not self._inside(self.work, target):
                return f"오류: 스크립트에 넘기는 파일은 작업 폴더({self.work.as_posix()}) 안에 있어야 합니다. 받은 값: {a}"
        r = subprocess.run(["node", str(script), *argv[1:]], cwd=d, capture_output=True,
                           text=True, encoding="utf-8", errors="replace", timeout=60)
        return json.dumps({"exit_code": r.returncode, "stdout": r.stdout[-6000:], "stderr": r.stderr[-2000:]}, ensure_ascii=False)


def trim_history(messages, keep_last=3, limit=300):
    """오래된 도구 결과를 짧게 줄여 컨텍스트를 아낀다.
    스킬 본문·참고 자료(<skill_…>)와 최근 keep_last개의 도구 결과는 그대로 둔다."""
    tool_idx = [i for i, m in enumerate(messages) if m.get("role") == "tool"]
    for i in tool_idx[:-keep_last] if keep_last else tool_idx:
        c = messages[i]["content"]
        if c.startswith("<skill_") or len(c) <= limit:
            continue
        messages[i] = {**messages[i], "content": c[:limit] + f"\n…(오래된 결과 {len(c) - limit}자 생략)"}
    return messages

def ask_openai(client, bridge, request, model="gpt-5.4-mini", max_steps=15):
    items = [{"role": "system", "content": bridge.system_prompt()},
             {"role": "user", "content": request}]
    for step in range(1, max_steps + 1):
        resp = client.responses.create(model=model, input=items, tools=bridge.tool_specs_responses())
        items += resp.output                                   # 모델의 응답(도구 호출 포함)을 기록에 쌓는다

        if not calls:                                          # 도구 호출이 없으면 = 최종 답
            return resp.output_text
        for c in calls:
            print(f"  → [{step}] {c.name} {c.arguments[:90]}")
            result = bridge.call(c.name, json.loads(c.arguments))
            items.append({"type": "function_call_output", "call_id": c.call_id, "output": result})
    return "(도구 호출 횟수 초과)"

# ─────────────────────────────────────────────────────────────
# 연결 B: transformers로 내 PC에서 직접 돌리는 Qwen.
#   모델은 도구 호출을 <tool_call>{...}</tool_call> "글자"로 쓸 뿐이다.
#   그 글자를 찾아 JSON으로 바꾸고(파싱), 실행하고, 결과를 돌려주는 일은 전부 이 코드가 한다.
# ─────────────────────────────────────────────────────────────
import json
import re
from skill_bridge import SkillBridge

TOOL_CALL = re.compile(r"<tool_call>\s*(\{.*?\})\s*</tool_call>", re.S)


def load_qwen(model_id="Qwen/Qwen3-4B-Instruct-2507"):
    import torch
    from transformers import AutoModelForCausalLM, AutoTokenizer
    print("GPU:", torch.cuda.get_device_name(0) if torch.cuda.is_available() else "없음 (CPU로 매우 느림)")
    tok = AutoTokenizer.from_pretrained(model_id)
    model = AutoModelForCausalLM.from_pretrained(model_id, torch_dtype="auto", device_map="auto")
    return tok, model


def make_generate(tok, model, max_new_tokens=1500):
    def generate(messages, tools):
        text = tok.apply_chat_template(messages, tools=tools, add_generation_prompt=True, tokenize=False)
        inputs = tok(text, return_tensors="pt").to(model.device)
        out = model.generate(**inputs, max_new_tokens=max_new_tokens, do_sample=False)
        return tok.decode(out[0][inputs["input_ids"].shape[1]:], skip_special_tokens=True)
    return generate


def make_text_llm(tok, model, max_new_tokens=1500):
    """도구 없이 글만 주고받는 llm(prompt) -> str. 고정 파이프라인(run_pipeline.py)에 쓴다."""
    def llm(prompt):
        text = tok.apply_chat_template([{"role": "user", "content": prompt}], add_generation_prompt=True, tokenize=False)
        inputs = tok(text, return_tensors="pt").to(model.device)
        out = model.generate(**inputs, max_new_tokens=max_new_tokens, do_sample=False)
        return tok.decode(out[0][inputs["input_ids"].shape[1]:], skip_special_tokens=True)
    return llm


def ask_qwen(generate, bridge, request, max_steps=15):
    messages = [{"role": "system", "content": bridge.system_prompt()},
                {"role": "user", "content": request}]
    tools = bridge.tool_specs()
    for step in range(1, max_steps + 1):
        reply = generate(messages, tools)
        calls = []
        for raw in TOOL_CALL.findall(reply):
            try:
                calls.append(json.loads(raw))
            except json.JSONDecodeError:
                pass                                            # 깨진 호출은 무시(아래에서 안내)
        text = TOOL_CALL.sub("", reply).strip()
        if not calls:
            if "<tool_call>" in reply:                         # 호출하려다 JSON을 망친 경우
                messages += [{"role": "assistant", "content": reply},
                             {"role": "user", "content": "도구 호출 JSON이 깨졌습니다. 올바른 JSON으로 다시 호출하세요."}]
                continue
            return text
        # 모델의 도구 호출을 기록에 남긴다 (Qwen 템플릿이 다음 턴에 <tool_call>로 다시 그려 줌)
        messages.append({"role": "assistant", "content": text,
                         "tool_calls": [{"type": "function", "function": {"name": c["name"], "arguments": c.get("arguments", {})}} for c in calls]})
        for c in calls:
            args = c.get("arguments", {})
            print(f"  → [{step}] {c['name']} {json.dumps(args, ensure_ascii=False)[:90]}")
            messages.append({"role": "tool", "content": bridge.call(c["name"], args)})
    return "(도구 호출 횟수 초과)"

def parse_json(text):
    m = re.search(r"\{.*\}", text, re.S)                 # 모델이 앞뒤에 말을 붙여도 JSON만 꺼낸다
    return json.loads(m.group(0)) if m else {}


def node(skill_dir, *args):
    r = subprocess.run(["node", *args], cwd=skill_dir, capture_output=True, text=True, encoding="utf-8", errors="replace", timeout=60)
    return r.returncode, r.stdout, r.stderr


def make_gian(llm, request, kit_dir, today=None):
    today = today or dt.date.today()
    kit = Path(kit_dir).resolve()
    skill = kit / ".agents" / "skills" / "writing-hwp-documents"
    work = kit / "work"
    work.mkdir(exist_ok=True)

    # ① 모델: 정보 뽑기
    f = parse_json(llm(EXTRACT.format(year=today.year, request=request)))
    print("뽑은 정보:", json.dumps(f, ensure_ascii=False))

    # ② 코드: 빠진 정보가 있으면 여기서 멈추고 묻는다 (모델의 판단에 맡기지 않음)
    missing = [label for key, label in REQUIRED.items() if not f.get(key)]
    if missing:
        return {"ok": False, "ask": missing}
    # 코드: 결재선 이름이 요청 글에 실제로 있는지 대조한다 (모델이 지어낸 이름 막기)
    made_up = [label for key, label in (("drafter", "기안자"), ("reviewer", "검토자"), ("approver", "결재권자"))
               if f[key].split()[-1] not in request]
    if made_up:
        return {"ok": False, "ask": [f"{x} 성명(요청에 없는 이름이 나옴)" for x in made_up]}

    # ③ 코드: 날짜·요일·시각 형식을 규칙대로 만든다
    d = dt.date.fromisoformat(f["date"])
    when = f"{d.year}. {d.month}. {d.day}.({WEEKDAY[d.weekday()]}) {f['start']}" + (f"~{f['end']}" if f.get("end") else "")
    lines = [f"# {f['title']}", "", f"- {f.get('purpose') or '다음과 같이 추진하고자 합니다.'}",
             f"  - 일시: {when}", f"  - 장소: {f['place']}"]
    if f.get("target"):
        lines.append(f"  - 대상: {f['target']}")
    if f.get("budget"):
        lines.append(f"  - 소요예산: {f['budget']}")
    draft = "\n".join(lines) + "\n"
    meta = {"head": {"org": ORG, "to": "내부결재"},
            "foot": {"sender": SENDER, "drafter": f["drafter"], "reviewer": f["reviewer"],
                     "approver": f["approver"], "docNum": "(확인 필요)"}}
    draft_p, meta_p = work / "draft.md", work / "meta.json"
    meta_p.write_text(json.dumps(meta, ensure_ascii=False, indent=2), encoding="utf-8")

    # ④ 검수 → (오류가 있으면) 모델에게 고치게 하고 다시 검수. 최대 2번.
    for attempt in range(3):
        draft_p.write_text(draft, encoding="utf-8")
        _, out, _ = node(skill, "scripts/check_draft.mjs", draft_p.as_posix(), "--type", "gian")
        report = json.loads(out)
        print(f"검수 {attempt + 1}회차: 오류 {report['errors']}건")
        if report["errors"] == 0:
            break
        if attempt == 2:
            return {"ok": False, "reason": "검수 오류가 남아 생성하지 않음", "findings": report["findings"]}
        findings = "\n".join(f"- {x['line']}행: {x['message']} → {x.get('suggest', '')}" for x in report["findings"] if x["severity"] == "error")
        draft = llm(FIX.format(draft=draft, findings=findings)).strip() + "\n"

    # ⑤ 생성 → 검증 (순서는 코드가 고정)
    key = re.sub(r"^\d{4}년\s*(상반기|하반기)?", "", f["title"])      # 파일명 핵심어: 연도 떼고 10자
    key = re.sub(r"[^0-9A-Za-z가-힣]", "", key)[:10]
    out_p = work / f"{today:%Y%m%d}_기안_{key}.hwpx"
    code, out, err = node(skill, "scripts/make_hwpx.mjs", draft_p.as_posix(), "--type", "gian",
                          "--meta", meta_p.as_posix(), "-o", out_p.as_posix())
    if code != 0:
        return {"ok": False, "reason": err.strip()}
    _, out, _ = node(skill, "scripts/verify_hwpx.mjs", out_p.as_posix(), "--expect", f["title"])
    v = json.loads(out)
    return {"ok": v["ok"], "file": out_p.as_posix(), "확인 필요": ["시행 문서번호"]}

from pathlib import Path

def find_kit(start):
    """start 폴더 아래에서 스킬의 SKILL.md를 찾아 kit 폴더 경로를 돌려준다."""
    for p in Path(start).rglob("writing-hwp-documents/SKILL.md"):
        return p.parents[3]            # SKILL.md → writing-hwp-documents → skills → .agents → kit
    raise FileNotFoundError(f"{start} 아래에 SKILL.md가 없습니다. 압축을 푼 위치를 확인하세요.")

KIT = find_kit(r"C:\Users\juhyu\Insights")     # 찾을 범위는 좁을수록 빠르다

사내 로컬 LLM에서의 설계 판단

  • "내부망에서 스킬이 수십 개 생긴다면, 스킬 구조로 로컬 LLM을 돌리는 게 맞을까, md 파일 여러 개를 폴더에 넣고 필요할 때 가이드라인을 참고하는 형태가 좋을까?"
한 줄 정리

모델이 작을수록 "다음에 무엇을 할지"의 판단을 코드로 옮깁니다. 실행해야 하는 일은 스킬로, 읽기만 하는 문서는 검색으로 나눕니다. 어느 쪽이든 kit의 스크립트는 그대로 씁니다.

가.두 가지 축으로 고르기

판단은 두 질문으로 정리됩니다. 쓸 모델이 여러 단계 도구 호출을 안정적으로 해내는가, 그리고 이 AI가 한 가지 일만 하는가 여러 가지 일을 하는가.

질문에 대한 답은 이렇습니다. 사내 로컬 LLM이 기안문·보고서 생성 하나만 한다면, 모델이 스킬을 고르고 절차를 스스로 따르는 방식은 과한 설계일 가능성이 큽니다. 스킬의 장점 중 "여러 개 중에서 알아서 고른다"는 고를 것이 하나뿐이면 쓸모가 없고, 그 판단은 작은 모델이 가장 자주 틀리는 부분입니다. 반면 스킬의 다른 장점, 곧 규칙 문서와 검사 스크립트를 한 폴더로 묶어 버전 관리하는 것은 그대로 유효합니다. 고정 파이프라인(8장 C)도 kit의 스크립트를 그대로 부릅니다.

반대로 여러 업무를 하는 사내 비서를 만든다면 스킬 형식이 맞습니다. 다만 작은 모델이면 자동 판단에 기대지 말고, 화면의 메뉴나 /이름으로 실행기가 스킬을 강제로 켜게 합니다.

나.스킬 수십 개 vs md 파일 폴더

숫자로 먼저 봅니다. 스킬 하나는 목록에 약 50~100토큰을 차지하고, 목록은 대화 시작부터 항상 들어갑니다.

그래서 "무엇을 스킬로 만들지"를 가려야 합니다. 스킬 후보는 두 종류로 나뉩니다.

실행형참고형
예HWP 생성, 전자결재 조회, 이자 계산문서 작성 관행, 부서별 규정, 용어집
모델에게 필요한 것도구를 불러 무언가를 실행내용을 읽고 참고
맞는 방식스킬 (절차 + 스크립트)검색(RAG): 질문과 관련된 조각만 찾아 넣기
개수가 늘면목록이 개수만큼 커짐검색 색인만 커지고, 매번 넣는 양은 거의 그대로

말씀하신 "md 파일 여러 개를 폴더에 넣고 필요할 때 가져다 참고"하는 방식이 바로 검색 방식입니다. 참고형 문서에는 이쪽이 스킬보다 맞습니다. 권하는 구조는 둘을 섞는 것입니다.

다.판단을 코드로 옮기는 여러 방법

  • 버튼·메뉴로 스킬 켜기. 사내 화면에서 "기안문 만들기"를 누르면 실행기가 activate_skill을 먼저 실행한 상태로 대화를 시작합니다. agent.mjs의 /이름 처리와 같은 원리입니다.
  • 빠진 정보 확인을 코드로. 필수 칸이 비었는지, 이름이 요청에 있었는지를 코드가 봅니다(8장 C).
  • 형식은 계산으로. 날짜·요일·금액 한글 표기처럼 규칙이 정해진 것은 모델에게 쓰게 하지 말고 코드가 만듭니다.
  • 틀리면 안 되는 일은 스크립트로. 검수, 자리표시자 차단, 결과 검증은 이미 스크립트입니다.

라.대화가 길어질 때: 오래된 결과 줄이기

2장에서 본 것처럼 대화 기록은 계속 쌓이고, 우리 agent.mjs에는 이를 줄이는 장치가 없습니다. 표준 구현 가이드는 대화를 줄일 때 "스킬 내용은 지우지 말라"고 하고, Claude 문서도 에이전트 작업에서 "오래된 도구 결과 지우기"를 한 방법으로 소개합니다. skill_bridge.py에 넣은 trim_history()가 이 둘을 합친 것입니다.

skill_bridge.py의 trim_history()
def trim_history(messages, keep_last=3, limit=300):
    """오래된 도구 결과를 짧게 줄여 컨텍스트를 아낀다.
    스킬 본문·참고 자료(<skill_…>)와 최근 keep_last개의 도구 결과는 그대로 둔다."""
    tool_idx = [i for i, m in enumerate(messages) if m.get("role") == "tool"]
    for i in tool_idx[:-keep_last] if keep_last else tool_idx:
        c = messages[i]["content"]
        if c.startswith("<skill_") or len(c) <= limit:
            continue
        messages[i] = {**messages[i], "content": c[:limit] + f"\n…(오래된 결과 {len(c) - limit}자 생략)"}
    return messages

쓰는 법은 모델을 부르기 직전에 한 줄 넣는 것입니다. 예를 들어 run_qwen.py의 generate() 첫 줄에 trim_history(messages)를 넣습니다. 같은 시험을 켜고 끄고 돌린 결과입니다.

마.사내 도입 순서 제안

  1. 모델 없이 검수기부터. check_draft.mjs와 사내 규칙 파일만으로도 "사람이 쓴 기안문의 표기 오류 찾기"라는 쓸모가 있습니다. 규칙 파일을 사내 실제 규정으로 바꾸는 일이 이 단계입니다.
  2. 고정 파이프라인으로 한 종류. 기안문 한 종류를 8장 C 방식으로 사내 모델에 붙입니다.
  3. 평가로 모델 고르기. 같은 시험 사례(11장)로 후보 모델을 비교합니다.
  4. 업무가 늘면 스킬 + 메뉴. 실행형 업무를 스킬로 늘리고, 작은 모델이면 메뉴로 켭니다.
  5. 참고 문서는 검색으로. 규정집·관행 문서는 검색 색인으로 모읍니다.
스스로 확인
Q1. 사내 로컬 LLM이 기안문 생성만 한다. 스킬 폴더(SKILL.md·규칙·스크립트)는 버려야 하나?

아닙니다. "모델이 스킬을 골라 켜는" 구조가 필요 없을 뿐, 규칙 문서와 스크립트는 고정 파이프라인에서도 그대로 씁니다. 나중에 여러 업무로 넓힐 때 스킬 형식이 그대로 이어집니다.

Q2. 부서별 업무 규정 md 파일 80개를 모두 스킬로 만들면 어떤 문제가 생기나?

목록만 영어 설명 기준 약 4,000~8,000토큰, 한국어 설명이면 1만 토큰 안팎이 되어 작은 컨텍스트에서는 한도를 넘기고, 모델이 80개 중에서 골라야 해 판단도 흔들립니다. 읽기만 하는 문서라면 검색 도구 하나 뒤에 두는 편이 맞습니다.

Q3. 대화를 줄일 때 SKILL.md 본문을 지우면 어떻게 되나?

오류는 나지 않지만, 모델이 절차와 규칙을 잊은 채 계속 일합니다. 눈에 띄지 않게 품질이 떨어지므로 스킬 내용은 줄이기 대상에서 빼야 합니다.

11

좋은 스킬 만드는 법

한 줄 정리

설명(description)이 켜짐을 정하고, 스크립트가 정확성을 지키고, 평가가 빈틈을 찾아 줍니다. 짧게 쓰고, 틀리면 안 되는 일은 코드로 옮기고, 실제로 돌려 보며 고칩니다.

가.평가를 먼저 만든다

Anthropic의 작성 지침은 긴 지시문을 쓰기 전에 평가부터 만들라고 권합니다. agentskills.io도 실제 과제에서 출발해 첫 실행 뒤 확인 항목을 더해 가라고 안내합니다. 순서는 이렇습니다.

  1. 스킬 없이 모델에게 먼저 시켜 봅니다.
  2. 틀리거나 모자란 점을 기록합니다.
  3. 그 빈틈을 메우는 만큼만 지시문과 스크립트를 씁니다.

그러면 상상 속 문제가 아니라 실제로 생기는 문제를 푸는 스킬이 됩니다.

나.description이 켜짐의 전부다

모델은 목록의 description만 보고 스킬을 켤지 정합니다(5장). 본문이 아무리 좋아도 설명이 부실하면 스킬은 쓰이지 않습니다.

  • 무엇을 하는지와 언제 쓰는지를 모두 적습니다.
  • 사용자가 실제로 쓰는 말을 넣습니다. "품의", "결재 올릴 문서", "한글 파일", "hwp"처럼 요청할 때 쓰는 표현입니다.
  • 쓰지 않을 경우를 적어 비슷한 요청과 경계를 긋습니다.
  • 문체는 Anthropic 지침처럼 3인칭 서술("~한다. ~할 때 사용한다.")도, agentskills.io 예시처럼 "~할 때 이 스킬을 쓴다"는 지시형도 됩니다. "무엇을·언제"가 분명한 것이 핵심입니다.
  • 짧게 씁니다. 표준 한도는 1,024자이고, 모든 스킬의 설명이 항상 컨텍스트에 올라갑니다. Claude Code는 목록에서 설명(description과 when_to_use를 합친 글)을 1,536자까지만 보여 줍니다.
나쁜 예와 좋은 예
# 나쁜 예: 무엇을 하는지도, 언제 쓰는지도 알 수 없음
description: 문서 작성을 도와줍니다.

# 좋은 예 (우리 스킬): 무엇 + 언제(사용자 표현) + 쓰지 않을 때
description: 사내 기안문과 보고서를 한글(HWPX) 파일로 작성한다. 사용자가 기안, 품의, 결재 올릴 문서, 검토보고, 보고서, 한글 파일, hwp, hwpx를 언급하거나 메모·회의 내용을 정식 사내 문서로 만들어 달라고 할 때 사용한다. 워드·엑셀·PDF 작성이나 기존 한글 파일을 읽고 요약만 하는 요청에는 사용하지 않는다.

다.본문은 짧게, 작은 모델에게는 예시로

  • 모델이 이미 아는 것은 뺍니다. 문장마다 "이 문장이 없으면 모델이 틀릴까?"를 묻고, 아니면 지웁니다.
  • 500줄 이하로 두고, 긴 내용은 참고 파일로 뺍니다. 참고 파일은 SKILL.md에서 한 단계로만 연결합니다. 참고 파일이 또 다른 파일을 가리키면 모델이 끝까지 따라가지 않을 수 있습니다.
  • 복사할 체크리스트를 둡니다. 모델이 답변에 체크리스트를 옮겨 적고 표시하게 하면 단계를 덜 건너뜁니다.
  • 조건에 따른 갈림길을 둡니다. "기안문이면 이 파일, 보고서면 저 파일"처럼 필요한 것만 읽게 합니다.
  • 명령은 그대로 복사할 수 있게 적고, 결과 해석법(errors가 1 이상이면 고친다)까지 적습니다.
  • "주의: 자주 틀리는 것"이 스킬에서 가장 값진 부분입니다. 모델이 실수할 때마다 여기에 한 줄씩 늘립니다.
  • 용어는 하나로. 우리 스킬은 끝까지 "원고"라고만 부르고 초안·draft를 섞지 않았습니다.
  • 작은 모델에게는 설명을 늘리기보다 예시·템플릿·스크립트를 늘립니다.

라.스크립트는 모델이 쓰는 프로그램이다

마.두 가지 평가

켜짐 평가: 필요할 때 켜지고, 아닐 때 안 켜지는가

  • 켜져야 할 질문과 켜지면 안 되는 질문을 각각 8~10개 만듭니다. "hwp 파일 요약해 줘"처럼 단어는 겹치지만 할 일이 다른 질문이 가장 쓸모 있습니다. 우리 evals/trigger-queries.json은 시작용으로 5개씩 들어 있습니다.
  • 모델은 확률적으로 움직이므로 질문마다 3번씩 돌려 켜진 비율을 봅니다.
  • 질문을 6:4로 나눠 6으로만 설명을 고치고, 4로 일반화됐는지 확인합니다.

결과물 평가: 결과가 좋은가

  • 사례마다 실제 말투의 요청(prompt), 기대 결과(expected_output), 확인 항목(assertions)을 적습니다.
  • 같은 요청을 스킬이 있을 때와 없을 때 각각 돌려 비교합니다. 스킬 없이도 잘 되는 항목은 덜어 낼 후보입니다.
  • 기계로 판정할 수 있는 것은 기계로 합니다. 우리 스킬에서는 verify_hwpx --expect와 check_draft의 errors == 0입니다.
  • 정보가 부족한 요청(3번 사례)을 꼭 넣습니다. "지어내지 않고 되묻는가"는 은행 문서에서 가장 중요한 품질입니다.

바.실제로 이 스킬을 고친 기록

스킬을 만든 직후 스크립트를 직접 돌려 보면서 세 가지를 발견해 고쳤습니다.

발견원인고친 곳
2,000,000 원이 검수를 통과함엔진 검사기에 금액 띄어쓰기 규칙이 없음house-rules.json에 규칙 한 줄 추가
"늘어난 것 같음"이 통과함금지 표현 정규식이 "인 것 같"만 잡음정규식을 넓힘
보고서 요약문에 경고가 뜸요약문 끝맺음 관행("~하고자 함.")이 규칙 파일에 없음report-rules.md와 템플릿 수정

고칠 때는 원인을 셋 중 하나로 가립니다. 지시가 모호했는지(SKILL.md·참고 문서), 규칙이 빠졌는지(규칙 파일), 스크립트가 틀렸는지(스크립트). 고친 뒤에는 모든 사례를 다시 돌려 다른 곳이 나빠지지 않았는지 봅니다.

사.보안: 스킬 설치는 프로그램 설치와 같다

  • 직접 만들었거나 검토를 마친 스킬만 씁니다. 스크립트뿐 아니라 SKILL.md와 참고 문서의 지시문도 코드처럼 검토합니다. 악성 지시는 글 속에 숨어 있을 수 있습니다.
  • 외부 URL에서 내용을 가져오는 스킬은 쓰지 않습니다.
  • 실행기 권한을 최소로 둡니다. 셸 대신 허용 목록, 작업 폴더 제한, 시간 제한(우리 tools.mjs, skill_bridge.py).
  • 남이 만든 프로젝트 폴더의 .agents/skills/에 스킬이 섞여 들어올 수 있습니다. 표준 구현 가이드도 프로젝트 스킬은 신뢰를 확인한 뒤 불러오라고 권합니다.
  • 은행 적용: 스킬 등록 심사, 변경 시 코드 리뷰, 배포본 해시 기록, 도구 호출 감사 로그(logs/audit.jsonl), 고객 실명·주민등록번호·계좌번호 차단 규칙.

아.운영

  • 머리말 metadata에 담당 부서와 버전을 적고, 스킬 폴더를 Git으로 관리합니다.
  • 짝을 이루는 파일(house-style.md와 house-rules.json)은 함께 고친다는 규칙을 둡니다.
  • 분기마다, 그리고 사내 모델을 바꿀 때마다 평가를 다시 돌립니다.
  • 엔진·의존성 버전을 고정하고, 올릴 때는 평가를 거친 뒤 올립니다.

자.제품별 추가 기능은 표준 밖이다

Claude Code는 표준에 없는 필드와 동작을 더 지원합니다. 다른 제품에서는 무시될 수 있으므로, 스킬의 핵심 동작은 표준 필드만으로 되게 만들고 이런 기능은 편의로만 씁니다.

차.한국어·윈도우·폐쇄망에서 챙길 것

  • 인코딩. 모든 파일은 UTF-8로 저장합니다. 편집기에서 ANSI(cp949)로 저장하면 한글이 깨지고, BOM이 붙은 UTF-8은 머리말을 못 읽는 실행기가 있습니다(우리 실행기는 BOM을 지우고 읽음).
  • 경로. SKILL.md 안에서는 scripts/check_draft.mjs처럼 슬래시로 적습니다.
  • 이름과 내용. name은 영문 소문자, 설명과 본문은 한국어. 사용자가 한국어로 요청하므로 설명에 한국어 표현이 있어야 잘 켜집니다.
  • 실행 중 다운로드 금지. npx처럼 그때그때 내려받는 명령은 폐쇄망에서 실패합니다. 의존성은 외부망에서 같은 운영체제로 npm ci해서 반입합니다.

용어집

스킬
에이전트가 특정 업무에 꺼내 쓰는 폴더. SKILL.md가 필수이고 스크립트·참고 문서·서식을 함께 담음
SKILL.md
스킬의 입구 파일. 머리말(이름·설명)과 본문(지시문)으로 구성
머리말(frontmatter)
파일 맨 위 --- 사이의 YAML. 이름·설명 같은 정보를 적음
점진적 공개
목록 → 지시문 → 자원 순으로 필요할 때만 모델에게 보여 주는 방식
실행기(하네스)
모델과 컴퓨터 사이의 중개 프로그램. 스킬을 찾아 알리고, 모델의 도구 호출을 실제로 실행함. 우리 runner/, Claude Code 등
토큰
모델이 글을 잘게 쪼개 세는 단위. 컨텍스트 창의 크기도 토큰으로 셈
컨텍스트 창
모델이 한 번에 참고할 수 있는 글의 양(만들어지는 답 포함). 실제 한도는 서버 설정이 정함
상태 없음(stateless)
모델이 호출 사이의 대화를 기억하지 않는 성질. 그래서 매 호출에 대화 전체를 다시 보냄
어텐션
각 토큰이 자기 앞의 모든 토큰을 한 번에 둘러보며 얼마나 참고할지 계산하는 방식. 길이가 N이면 비교가 약 N×N÷2
컨텍스트 부패
입력이 길어질수록 정확도와 기억이 떨어지는 현상(context rot)
도구 호출
모델이 "이 도구를 이 값으로 불러 달라"고 JSON으로 요청하는 것(function calling). 실행은 모델 밖의 코드가 함
파싱(해석)
모델이 쓴 글에서 도구 호출을 찾아 구조화된 값으로 바꾸는 일. 서버가 하거나(OpenAI·vLLM·Ollama) 우리 코드가 함(transformers)
채팅 템플릿
대화 기록과 도구 설명서를 모델이 학습한 모양의 긴 글 하나로 바꾸는 규칙(apply_chat_template)
OpenAI 호환 API
OpenAI의 메시지·도구 호출 형식을 따르는 API. vLLM, Ollama 등 사내 LLM 서버가 제공
에이전트형
모델이 다음에 할 일을 스스로 정하며 도구를 부르는 방식
고정 파이프라인
순서는 코드가 정하고 모델은 정해진 좁은 일만 하는 방식
MCP
모델을 외부 시스템(DB, 결재 시스템 등)에 연결하는 표준 규약
RAG(검색 증강)
질문과 관련된 문서 조각을 검색해 그때그때 모델에게 넣어 주는 방식
엔진
실제로 파일을 만드는 라이브러리. 이 자료에서는 kordoc
HWPX · OWPML
zip과 XML로 된 한/글의 개방형 문서 형식. 국가표준 KS X 6101
상대경로 · 절대경로
"지금 기준 폴더에서 어디"로 적는 경로와, C:\…처럼 처음부터 적는 경로
npm ci · node_modules
lock 파일대로 패키지를 설치하는 명령과, 그 결과가 담기는 폴더
.mjs
import/export 문법을 쓰는 자바스크립트 파일 확장자
평가(eval)
정해진 사례로 스킬이 제대로 켜지고 결과가 좋은지 시험하는 것
암묵지
문서화되지 않고 사람에게서 사람으로 전해지는 업무 요령. 스킬의 참고 문서가 담을 핵심
