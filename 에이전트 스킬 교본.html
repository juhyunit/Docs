0.이 자료 사용법

이 자료를 끝까지 따라가면 다음을 할 수 있습니다.

  • 스킬이 무엇이고 왜 쓰는지 다른 사람에게 설명하기
  • 스킬이 실행되는 과정을 단계별로 이해하고, 스킬을 돌리는 실행기 코드를 읽기
  • 사내 로컬 LLM에서 스킬을 쓸 수 있는지, 무엇을 조심해야 하는지 판단하기
  • HWP 기안문·보고서 스킬을 파일 단위로 직접 만들고 테스트하기

본문에 나오는 스킬(writing-hwp-documents)과 실행기(runner)는 실제로 만들어 실행한 코드입니다. 스킬은 공식 검증 도구(skills-ref)를 통과했고, 테스트용 모의 모델로 요청 → 원고 작성 → 검수 → 수정 → 파일 생성 → 검증 전 과정을 확인했습니다.

확인하지 못한 것

실제 사내 LLM으로는 아직 돌려 보지 않았고, 만든 HWPX 파일을 한컴오피스에서 직접 열어 보지도 못했습니다(검증은 파일 구조 검사기와 재판독으로 했습니다). 사내에서 Ⅵ장의 평가를 한 번 거친 뒤 쓰시기 바랍니다.

읽는 순서. 처음이라면 Ⅰ·Ⅱ장만 읽어도 개념이 잡힙니다. 직접 만들 분은 Ⅴ장을 옆에 띄워 두고 따라 하세요. 코드 블록 오른쪽 위의 복사 버튼으로 파일 내용을 그대로 가져갈 수 있습니다.

Ⅰ스킬이란 무엇인가

가.한 문장 정의

스킬(Agent Skill)은 AI 에이전트가 특정 업무를 할 때 꺼내 보는 업무 매뉴얼 폴더입니다. 폴더 안에 SKILL.md라는 문서가 하나 반드시 있고, 필요하면 스크립트·참고 자료·서식 파일을 함께 넣습니다.

스킬 폴더의 기본 모양
writing-hwp-documents/     ← 스킬 폴더 (폴더 이름 = 스킬 이름)
├── SKILL.md               ← 필수: 이름·설명 + 작업 지시문
├── references/            ← 선택: 필요할 때만 읽는 참고 문서
├── scripts/               ← 선택: 실행하는 프로그램
└── assets/                ← 선택: 서식, 템플릿, 데이터

SKILL.md는 두 부분으로 되어 있습니다. 맨 위 --- 사이의 머리말(frontmatter)에 이름과 설명을 적고, 그 아래 본문에 작업 방법을 적습니다.

가장 작은 SKILL.md
---
name: writing-hwp-documents
description: 사내 기안문과 보고서를 한글(HWPX) 파일로 작성한다. ... 할 때 사용한다.
---

나.비유: 신입사원과 업무 매뉴얼 바인더

비유

다.왜 필요해졌나: 프롬프트만으로 부족한 점

  • 매번 붙여넣기. 긴 작성 규칙을 대화마다 복사해 넣어야 합니다.
  • 작업 기억 낭비. 모델이 한 번에 기억하는 양(컨텍스트 창)은 정해져 있습니다. 기안문 규칙과 보고서 규칙을 처음부터 다 넣으면 한쪽은 늘 쓸모없는 짐이 됩니다.
  • 관리 불가. 누가 어떤 버전의 프롬프트를 쓰는지 알 수 없고, 규칙을 고쳐도 전파되지 않습니다.
  • 정확성의 한계. "날짜는 2026. 9. 25. 형식으로"라고 써 둬도 모델은 가끔 틀립니다. 검사 프로그램을 같이 주면 틀린 곳을 기계가 찾아 줍니다.

스킬은 이 네 가지를 폴더 하나로 해결합니다. 필요할 때만 읽으니 작업 기억을 아끼고, 파일이니 버전 관리와 공유가 되고, 프로그램을 같이 담으니 정확해집니다.

라.스킬이 하지 않는 것

핵심

Ⅱ스킬은 어떻게 작동하나

가.핵심 원리: 점진적 공개

스킬은 세 단계로 나뉘어 모델에게 보입니다. 처음에는 목록만, 쓰기로 하면 본문을, 본문이 가리키는 파일은 필요할 때만 보여 줍니다.

단계모델이 보는 것언제크기
1. 목록name + description대화 시작부터 항상스킬당 약 50~100토큰
2. 지시문SKILL.md 본문 전체모델이 이 스킬을 쓰기로 했을 때5,000토큰 이하·500줄 이하 권장
3. 자원참고 문서, 서식, 스크립트 실행 결과지시문이 가리키고 실제로 필요할 때읽은 만큼만

토큰은 모델이 글을 잘게 쪼개 세는 단위입니다. 한국어 한 글자가 몇 토큰인지는 모델마다 다릅니다.

나.그래서 스킬을 많이 설치해도 괜찮다

스킬 100개를 설치해도 목록은 100 × 약 100토큰 = 약 1만 토큰입니다. 반대로 100개 스킬의 본문(각 3,000토큰이라고 치면)을 처음부터 다 넣으면 30만 토큰이 되어 대부분의 모델이 한 번에 담지 못합니다. 목록만 들고 다니다가 필요한 한두 개만 펼치기 때문에 설치 개수를 크게 걱정하지 않아도 됩니다. 단, 컨텍스트 창이 작은 로컬 모델은 사정이 다릅니다(Ⅳ장 라).

가.네 개의 층과 층 사이의 약속

  • 모델. 글을 읽고 쓰며, "이 도구를 이 인자로 불러 달라"는 요청을 JSON으로 냅니다. 파일을 직접 만지지 못합니다.
  • 실행기(하네스, harness). 모델과 컴퓨터 사이의 중개자입니다. 스킬을 찾아 목록을 만들고, 모델의 도구 요청을 실제로 실행합니다. Claude Code, Codex, Gemini CLI 같은 제품이 이 역할을 하고, 사내용은 아래처럼 직접 만들 수 있습니다.
  • 스킬. 업무 지식과 절차(글), 검사·생성 도구(스크립트)를 담은 폴더입니다.
  • 엔진. 실제로 HWPX 파일을 만드는 라이브러리입니다. 스킬의 스크립트가 부릅니다. 엔진은 스크립트 안에 숨은 부품이고, 스킬은 그 부품을 언제 어떻게 쓰라고 적은 매뉴얼입니다.

나.실행기가 해야 하는 다섯 가지 일

agentskills.io의 구현 가이드는 실행기의 일을 다섯 단계로 정리합니다. 우리 실행기도 이 순서를 따릅니다.

  1. 찾기. 정해진 폴더에서 SKILL.md가 있는 하위 폴더를 찾습니다. .agents/skills/는 여러 제품이 함께 쓰는 관례 위치입니다. 같은 이름이 겹치면 프로젝트 폴더의 스킬이 사용자 폴더의 스킬보다 우선합니다.
  2. 읽기. 머리말에서 name과 description만 꺼냅니다. 규칙이 조금 어긋나도 경고만 하고 불러오는 "관대한 검증"을 권장합니다. description이 없으면 모델이 언제 쓸지 알 수 없으므로 그 스킬만 건너뜁니다.
  3. 알리기. 목록을 시스템 프롬프트에 넣고 "맞는 스킬이 있으면 먼저 불러오라"는 짧은 안내를 붙입니다. 스킬이 하나도 없으면 목록과 안내를 아예 넣지 않습니다. 빈 목록은 모델을 헷갈리게 합니다.
  4. 켜기와 실행. 모델이 스킬을 고르면 본문을 넘겨주고, 본문이 가리키는 파일 읽기와 스크립트 실행을 처리합니다.
  5. 관리. 이미 켠 스킬은 다시 넣지 않습니다. 대화가 길어져 오래된 내용을 줄일 때도 스킬 지시문은 지우지 않아야 합니다. 지워지면 모델이 규칙을 잊은 채 계속 일합니다.

export function discoverSkills(projectDir) {
  const skills = new Map()
  const warnings = []
  for (const root of skillRoots(projectDir)) {
    if (!existsSync(root)) continue
    for (const entry of readdirSync(root, { withFileTypes: true })) {
      if (!entry.isDirectory() || entry.name.startsWith(".") || entry.name === "node_modules") continue
      const location = join(root, entry.name, "SKILL.md")
      if (!existsSync(location)) continue
      const parsed = parseSkillFile(location)
      if (parsed.error) { warnings.push(`${location}: ${parsed.error} → 건너뜀`); continue }
      const { name, description } = parsed.meta
      if (!description) { warnings.push(`${location}: description이 없어 건너뜀`); continue }
      if (name && name !== entry.name) warnings.push(`${location}: name(${name})과 폴더 이름(${entry.name})이 다름`)
      const key = name || entry.name
      if (skills.has(key)) warnings.push(`스킬 이름 충돌 '${key}': ${location} 을(를) 사용`)
      skills.set(key, { name: key, description, location, dir: dirname(location) })
    }
  }
  return { skills, warnings }
}

export function catalogXml(skills) {
  const items = [...skills.values()].map((s) =>
    `  <skill>\n    <name>${esc(s.name)}</name>\n    <description>${esc(s.description)}</description>\n  </skill>`)
  return `<available_skills>\n${items.join("\n")}\n</available_skills>`
}

  function runScript(skillName, command) {
    const skill = skills.get(skillName)
    if (!skill) return `오류: '${skillName}' 스킬이 없습니다.`
    if (!activated.has(skillName)) return `오류: 먼저 activate_skill로 '${skillName}' 스킬을 불러오세요.`
    if (/[;&|`$<>]/.test(command)) return "오류: 셸 기호(; & | ` $ < >)는 쓸 수 없습니다. 스크립트 명령 하나만 주세요."
    const argv = splitArgs(command)
    if (["node", "python3", "python"].includes(argv[0])) argv.shift() // "node scripts/x.mjs" 형태도 받아 준다
    const script = resolve(skill.dir, argv[0] ?? "")
    if (!inside(join(skill.dir, "scripts"), script) || !existsSync(script)) {
      return `오류: 이 스킬의 scripts/ 안에 있는 파일만 실행할 수 있습니다. 받은 값: ${argv[0]}\n` +
        `사용 가능: ${listResources(skill.dir).filter((f) => f.startsWith("scripts/")).join(", ")}`
    }
    const interpreter = INTERPRETERS[extname(script)]
    if (!interpreter) return `오류: 실행할 수 없는 파일 형식입니다: ${extname(script)}`
    const r = spawnSync(interpreter, [script, ...argv.slice(1)], {
      cwd: skill.dir, encoding: "utf8", timeout: SCRIPT_TIMEOUT_MS, shell: false,
    })
    const result = { exit_code: r.status ?? -1, stdout: clip(r.stdout ?? ""), stderr: clip(r.stderr ?? "") }
    if (r.error) result.stderr += `\n실행 오류: ${r.error.message}`
    return JSON.stringify(result, null, 2)
  }

export function skillRoots(projectDir) {
  return [
    join(homedir(), ".agents", "skills"), // 사용자 단위 (모든 프로젝트 공용)
    join(projectDir, ".agents", "skills"), // 프로젝트 단위 (다른 도구와 같은 위치 규칙)
  ]

// 간이 YAML 파서. SKILL.md 머리말에 쓰이는 형태만 지원한다:
//   key: value / key: "value" / key: > 또는 | 여러 줄 / key: 다음 줄부터 들여쓴 하위 항목(metadata)
function parseFrontmatter(text) {
  const out = {}
  const lines = text.split(/\r?\n/)
  for (let i = 0; i < lines.length; i++) {
    const m = lines[i].match(/^([A-Za-z0-9_-]+):\s*(.*)$/)
    if (!m) continue
    const [, key, rawValue] = m
    const value = rawValue.trim()
    if (value === ">" || value === "|" || value === ">-" || value === "|-") {
      const block = []
      while (i + 1 < lines.length && /^\s+\S/.test(lines[i + 1])) block.push(lines[++i].trim())
      out[key] = value.startsWith(">") ? block.join(" ") : block.join("\n")
    } else if (value === "") {
      const map = {}
      while (i + 1 < lines.length && /^\s+\S/.test(lines[i + 1])) {
        const sub = lines[++i].trim().match(/^([A-Za-z0-9_-]+):\s*(.*)$/)
        if (sub) map[sub[1]] = unquote(sub[2].trim())
      }
      out[key] = map
    } else {
      out[key] = unquote(value)
    }
  }
  return out
}
const unquote = (v) => v.replace(/^"(.*)"$/, "$1").replace(/^'(.*)'$/, "$1")

export function parseSkillFile(path) {
  const raw = readFileSync(path, "utf8").replace(/^﻿/, "") // 윈도우 메모장이 붙이는 BOM 제거
  const m = raw.match(/^---\r?\n([\s\S]*?)\r?\n---\r?\n?([\s\S]*)$/)
  if (!m) return { error: "첫 줄이 ---로 시작하는 머리말(frontmatter)이 없음" }
  return { meta: parseFrontmatter(m[1]), body: m[2].trim() }
}

      const parsed = parseSkillFile(location)
      if (parsed.error) { warnings.push(`${location}: ${parsed.error} → 건너뜀`); continue }

const MAX_OUTPUT = 8000 // 도구 결과가 너무 길면 모델 컨텍스트를 낭비한다. 잘라서 준다.
const SCRIPT_TIMEOUT_MS = 60_000 // 문서 생성은 보통 수 초 안에 끝난다. 1분이면 충분히 여유 있다.
const INTERPRETERS = { ".mjs": process.execPath, ".js": process.execPath, ".py": "python3" }

// target이 base 폴더 안(또는 base 자체)인지 확인한다. "../" 로 빠져나가는 경로를 막는다.
const inside = (base, target) => {
  const rel = relative(resolve(base), resolve(target))
  return rel === "" || (rel !== ".." && !rel.startsWith(".." + sep) && !isAbsolute(rel))
}
const clip = (s) => (s.length > MAX_OUTPUT ? s.slice(0, MAX_OUTPUT) + `\n…(${s.length - MAX_OUTPUT}자 생략)` : s)

// 따옴표를 지키며 명령 문자열을 인자 배열로 나눈다. 셸을 거치지 않으므로 ; && | 같은 기호가 명령으로 해석되지 않는다.
function splitArgs(command) {
  const out = []
  const re = /"([^"]*)"|'([^']*)'|(\S+)/g
  let m
  while ((m = re.exec(command))) out.push(m[1] ?? m[2] ?? m[3])
  return out
}

function listResources(dir) {
  const files = []
  const walk = (d) => {
    for (const e of readdirSync(d, { withFileTypes: true })) {
      if (e.name === "node_modules" || e.name.startsWith(".")) continue
      const p = join(d, e.name)
      if (e.isDirectory()) walk(p)
      else if (e.name !== "SKILL.md") files.push(relative(dir, p).split(sep).join("/"))
    }
  }
  walk(dir)
  return files.slice(0, 50)
}

export function createTools({ skills, workDir, log }) {
  const activated = new Set()
  const names = [...skills.keys()]

  // 스킬 본문을 구조화된 태그로 감싸서 준다. 모델이 스킬 지시문을 다른 대화와 구분할 수 있고,
  // 하네스는 나중에 컨텍스트를 줄일 때 이 부분을 지우지 않도록 식별할 수 있다.
  function activate(name) {
    const skill = skills.get(name)
    if (!skill) return `오류: '${name}' 스킬이 없습니다. 사용 가능: ${names.join(", ")}`
    if (activated.has(name)) return `'${name}' 스킬은 이미 불러와 있습니다. 앞의 지시를 계속 따르세요.`
    activated.add(name)
    const { body } = parseSkillFile(skill.location)
    const resources = listResources(skill.dir).map((f) => `  <file>${f}</file>`).join("\n")
    return `<skill_content name="${name}">\n${body}\n\n스킬 폴더: ${skill.dir}\n` +
      `이 스킬의 상대경로(scripts/, references/, assets/)는 스킬 폴더 기준이다. 파일을 읽을 때는 절대경로를 쓴다.\n` +
      `스크립트는 run_script 도구로 실행한다.\n<skill_resources>\n${resources}\n</skill_resources>\n</skill_content>`
  }

  function readFile(path) {
    const p = resolve(path)
    const allowed = [...skills.values()].some((s) => inside(s.dir, p)) || inside(workDir, p)
    if (!allowed) return `오류: 읽기가 허용되지 않은 경로입니다: ${p}\n스킬 폴더나 작업 폴더(${workDir}) 안의 파일만 읽을 수 있습니다.`
    if (!existsSync(p)) return `오류: 파일이 없습니다: ${p}`
    return clip(readFileSync(p, "utf8"))
  }

  function writeFile(path, content) {
    const p = resolve(workDir, path)
    if (!inside(workDir, p)) return `오류: 쓰기는 작업 폴더(${workDir}) 안에서만 할 수 있습니다.`
    mkdirSync(dirname(p), { recursive: true })
    writeFileSync(p, content)
    return `저장했습니다: ${p} (${Buffer.byteLength(content)}바이트)`
  }

  function runScript(skillName, command) {
    const skill = skills.get(skillName)
    if (!skill) return `오류: '${skillName}' 스킬이 없습니다.`
    if (!activated.has(skillName)) return `오류: 먼저 activate_skill로 '${skillName}' 스킬을 불러오세요.`
    if (/[;&|`$<>]/.test(command)) return "오류: 셸 기호(; & | ` $ < >)는 쓸 수 없습니다. 스크립트 명령 하나만 주세요."
    const argv = splitArgs(command)
    if (["node", "python3", "python"].includes(argv[0])) argv.shift() // "node scripts/x.mjs" 형태도 받아 준다
    const script = resolve(skill.dir, argv[0] ?? "")
    if (!inside(join(skill.dir, "scripts"), script) || !existsSync(script)) {
      return `오류: 이 스킬의 scripts/ 안에 있는 파일만 실행할 수 있습니다. 받은 값: ${argv[0]}\n` +
        `사용 가능: ${listResources(skill.dir).filter((f) => f.startsWith("scripts/")).join(", ")}`
    }
    const interpreter = INTERPRETERS[extname(script)]
    if (!interpreter) return `오류: 실행할 수 없는 파일 형식입니다: ${extname(script)}`
    const r = spawnSync(interpreter, [script, ...argv.slice(1)], {
      cwd: skill.dir, encoding: "utf8", timeout: SCRIPT_TIMEOUT_MS, shell: false,
    })
    const result = { exit_code: r.status ?? -1, stdout: clip(r.stdout ?? ""), stderr: clip(r.stderr ?? "") }
    if (r.error) result.stderr += `\n실행 오류: ${r.error.message}`
    return JSON.stringify(result, null, 2)
  }

  // OpenAI 호환 API의 도구(function calling) 정의. 스킬 이름은 enum으로 제한해 모델이 없는 이름을 지어내지 못하게 한다.
  const definitions = [
    { type: "function", function: {
      name: "activate_skill",
      description: "작업이 스킬 설명과 맞으면 이 도구로 스킬의 전체 지시문을 불러온다. 지시문을 읽기 전에는 작업을 시작하지 않는다.",
      parameters: { type: "object", properties: { name: { type: "string", enum: names } }, required: ["name"] },
    } },
    { type: "function", function: {
      name: "read_file",
      description: "스킬 폴더나 작업 폴더 안의 텍스트 파일을 읽는다. 절대경로를 쓴다.",
      parameters: { type: "object", properties: { path: { type: "string" } }, required: ["path"] },
    } },
    { type: "function", function: {
      name: "write_file",
      description: "작업 폴더 안에 텍스트 파일을 저장한다(원고.md, meta.json 등). 같은 이름이면 덮어쓴다.",
      parameters: { type: "object", properties: { path: { type: "string" }, content: { type: "string" } }, required: ["path", "content"] },
    } },
    { type: "function", function: {
      name: "run_script",
      description: "불러온 스킬의 scripts/ 안 스크립트를 실행한다. command는 SKILL.md에 적힌 명령 그대로. 예: node scripts/check_draft.mjs /work/draft.md --type gian",
      parameters: { type: "object", properties: { skill: { type: "string", enum: names }, command: { type: "string" } }, required: ["skill", "command"] },
    } },
  ]

  async function call(name, args) {
    let result
    switch (name) {
      case "activate_skill": result = activate(args.name); break
      case "read_file": result = readFile(args.path); break
      case "write_file": result = writeFile(args.path, args.content ?? ""); break
      case "run_script": result = runScript(args.skill, args.command ?? ""); break
      default: result = `오류: 알 수 없는 도구 ${name}`
    }
    log({ event: "tool", name, args: name === "write_file" ? { path: args.path, chars: (args.content ?? "").length } : args, ok: !result.startsWith("오류") })
    return result
  }

  return { definitions, call, activate, activated }
}

  }

핵심

원리상 모델과 무관하게 돌아갑니다. 스킬은 모델의 기능이 아니라 실행기의 기능이기 때문입니다. 모델 입장에서 스킬은 "시스템 프롬프트에 적힌 목록"과 "도구로 받아 보는 글"일 뿐이고, 이는 어떤 모델에게나 똑같은 텍스트입니다. 위 그림에서 보듯 파일을 읽고 실행하는 쪽은 실행기입니다.

다만 "돌아간다"와 "잘 돌아간다"는 다릅니다. 아래 네 가지 조건이 맞아야 잘 돌아갑니다.

나.잘 돌아가기 위한 네 가지 조건

  1. 실행기가 스킬을 지원할 것. 제품이 지원하거나(Claude Code, Codex, Gemini CLI 등) 우리처럼 직접 구현해야 합니다. 모델 API만 호출하는 단순한 챗봇 화면은 스킬을 모릅니다.
  2. 모델이 도구 호출(function calling)을 할 것. 스킬을 켜고, 파일을 읽고, 스크립트를 돌리는 모든 동작이 도구 호출입니다.
  3. 모델이 지시를 따르고 판단할 것. 목록만 보고 스스로 켜는 판단, 긴 지시문의 순서를 끝까지 지키는 능력이 필요합니다. 모델의 크기와 품질에 크게 좌우됩니다.
  4. 스크립트를 실행할 환경이 있을 것. scripts/를 쓰는 스킬은 실행기가 코드를 실행할 수 있어야 합니다. 지시문만 있는 스킬은 이 조건이 필요 없습니다.

# 한글(HWPX) 사내 문서 작성

## 주의: 자주 틀리는 것

- 항목부호(`1.` `가.` `1)` 또는 `□` `○` `-`)는 직접 쓰지 않는다. 목록 들여쓰기(2칸)로 단계를 표현하면 엔진이 문서 종류에 맞는 부호를 붙인다.
- `끝.`은 원고에 쓰지 않는다. 기안문이면 엔진이 자동으로 붙인다.
- 날짜는 `2026. 9. 25.`, 시각은 `14:30`, 금액은 `금15,000,000원(금일천오백만원)` 형식이다.
- `붙임` 뒤에는 쌍점 없이 두 칸을 띄운다: `붙임  교육 일정표 1부.`
- 기안문 본문은 "~하고자 합니다", "~하시기 바랍니다"로, 보고서는 "~함", "~임" 같은 명사형으로 끝낸다.
- 고객 실명, 주민등록번호, 계좌번호는 원고에 넣지 않는다. 꼭 필요하면 `홍○○`, `***-**-****`처럼 가린다.
- 스크립트가 실패하면 오류 메시지의 안내를 따른다. 같은 명령을 그대로 반복하지 않는다.

# 기안문 작성 규칙

## 목차

- 본문 쓰는 순서
- 좋은 예
- 자주 하는 실수

## 구성: 원고와 meta.json에 나눠 쓰는 것

기안문은 두문, 본문, 결문 세 부분으로 되어 있다. 원고(draft.md)에는 **본문만** 쓰고, 두문과 결문은 meta.json에 쓴다. 엔진이 두문과 결문을 표 서식으로 그려 준다.

| 부분 | 들어가는 내용 | 쓰는 곳 |
|---|---|---|
| 두문 | 기관명, 수신, (경유) | meta.json의 `head` |
| 본문 | 제목, 내용, 붙임 | draft.md |
| 결문 | 발신명의, 결재선(기안·검토·결재), 시행 번호 | meta.json의 `foot` |

- 수신: 부서 안에서 결재만 받는 문서는 `내부결재`, 다른 부서로 보내면 `○○부장(○○팀장)`
- 결재선: `"직위 성명"` 형식으로 쓴다. 예: `"drafter": "대리 홍길동"`
- 시행 번호: `부서명-번호(시행일)`. 번호를 모르면 `(확인 필요)`로 둔다.

## 본문 쓰는 순서

1. 제목: `# 제목` 한 줄. 무엇을 하려는지 명사형으로 끝낸다.
   - 좋음: `# 2026년 하반기 디지털 역량 교육 실시`
   - 나쁨: `# 디지털 역량 교육 실시에 관한 건`
2. 첫 항목은 근거: `- 관련: 인재개발부-1234(2026. 9. 1.)`. 근거 문서가 없으면 이 항목을 뺀다.
3. 둘째 항목은 목적과 요청: `- (무엇)을 다음과 같이 실시하고자 합니다.`
4. 세부 사항은 그 아래 하위 목록(2칸 들여쓰기)으로. 순서는 일시 → 장소 → 대상 → 내용 → 소요예산.
5. 첨부가 있으면 본문 마지막에 붙임 줄을 둔다 (표기법은 notation-rules.md).

## 좋은 예

draft.md:

```markdown
# 2026년 하반기 디지털 역량 교육 실시

- 관련: 인재개발부-1234(2026. 9. 1.)
- 영업점 책임자의 디지털 역량을 높이기 위해 다음과 같이 교육을 실시하고자 합니다.
  - 일시: 2026. 10. 15.(목) 14:00~17:00
  - 장소: 본점 3층 대회의실
  - 대상: 영업점 책임자 40명
  - 소요예산: 금2,000,000원(금이백만원)

붙임  교육 일정표 1부.
```

meta.json:

```json
{
  "head": { "org": "가나다은행", "to": "내부결재" },
  "foot": {
    "sender": "가나다은행장",
    "drafter": "대리 홍길동",
    "reviewer": "팀장 김철수",
    "approver": "부장 박영희",
    "docNum": "인재개발부-(확인 필요)"
  }
}
```

엔진이 만든 결과: 제목 아래 `1. 관련: …`, `2. 영업점 책임자의 …`, 그 아래 `가. 일시`, `나. 장소` … 순으로 부호가 붙고, 붙임 뒤에 `끝.`이 자동으로 들어간다.

## 자주 하는 실수

- 제목에 "~에 관한 건", "~의 건"을 붙인다 → "~ 실시", "~ 승인 요청"처럼 핵심만 쓴다.
- 세부 사항을 한 문단에 줄글로 이어 쓴다 → 하위 목록으로 한 줄씩 나눈다.
- 근거 문서번호나 예산 금액을 지어낸다 → 자료에 없으면 쓰지 않거나 `(확인 필요)`로 표시한다.
- 본문을 "~한다", "~함"으로 끝낸다 → 기안문은 "~하고자 합니다", "~하시기 바랍니다"를 쓴다.

## 구성

```markdown
# 보고서 제목

> 한 줄 요약: [근거]하여 [목적]하고자 함. (60자 안팎)

## 추진배경
## 현황
## 문제점
## 개선방안
## 기대효과
## 향후계획
```

- 여섯 개 절을 다 쓸 필요는 없다. 자료에 있는 내용만큼 골라 쓴다. 보통 3~4개면 충분하다.
- 제목 바로 아래 `>` 인용문 한 줄은 요약 상자로 표시된다. 결론을 먼저 쓰고 "~하고자 함."으로 끝낸다.
- 각 절은 목록으로 쓴다. 1단계(□로 표시됨)는 핵심 주장, 2단계(○)는 근거와 수치, 3단계(-)는 세부 사항.

## 개조식 문체

- 문장을 "~다."로 끝내지 않는다. "~함", "~임", "~필요", "~예정" 또는 명사로 끝낸다.
  - 나쁨: `비대면 거래 비중이 크게 늘었다.`
  - 좋음: `비대면 거래 비중 급증`
- 한 항목은 한 줄, 40자 안팎으로 쓴다. 길어지면 하위 항목으로 나눈다.
- 물음표, 느낌표, 수사적 표현("획기적", "혁신적")을 쓰지 않는다.
- 수치에는 비교 기준을 붙인다: `58%(전년 대비 17%p 증가)`
- 출처가 있는 수치는 괄호로 출처를 단다: `(2026. 6. 말 기준, 영업기획부)`

## 좋은 예

```markdown
# 영업점 디지털 창구 확대 검토

> 디지털 창구 설치 점포의 대기시간 단축 효과를 확인하여 12개 점포에 추가 설치하고자 함.

## 추진배경
- 비대면 거래 비중 급증
  - 58%(전년 대비 17%p 증가, 2026. 6. 말 기준)

## 현황
- 디지털 창구 설치 점포 30개(전체 120개 중 25%)
  - 설치 점포의 창구 대기시간 평균 12분 → 7분

## 향후계획
- 2026. 10. 중 설치 대상 12개 점포 확정
- 2026. 12. 중 설치 완료 후 효과 분석 보고
```

| 시각 | `14:30`, `09:05` | `오후 2시 30분`, `2:30 PM`, `9:5` |

- 날짜는 연·월·일 글자를 빼고 온점을 찍는다. 온점 뒤는 한 칸 띄우고 마지막에도 온점을 찍는다.
- 월·일 앞에 0을 붙이지 않는다. 시각은 24시각제로 쓰고 시·분 앞에 0을 붙인다.

## 금액

- 형식: `금` + 아라비아 숫자 + `원` + 괄호 안 한글 금액
- 예: `금113,560원(금일십일만삼천오백육십원)`
- 숫자와 `원` 사이를 띄우지 않는다 (금액 변조 방지).
- 표 안이나 보고서처럼 한글 병기가 번거로운 곳은 `1억 2,000만원`처럼 쓸 수 있다.

## 항목부호 (엔진이 자동으로 붙임)

원고에서는 목록 들여쓰기로만 단계를 표현한다. 참고로 기안문의 부호 순서는 다음과 같다.

| 단계 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|
| 부호 | `1.` | `가.` | `1)` | `가)` | `(1)` | `(가)` | `①` | `㉮` |

보고서는 `□` → `○` → `-` → `·` 순서다.

## 붙임

- `붙임` 다음에 쌍점(:)을 쓰지 않고 두 칸 띄운다. 끝에 수량과 온점을 쓴다.
- 1개: `붙임  교육 일정표 1부.`
- 2개 이상: 번호를 붙인다.

```text
붙임  1. 교육 일정표 1부.
      2. 참석자 명단 1부.
```

## 끝 표시 (엔진이 자동으로 붙임)

- 기안문은 본문(또는 붙임) 마지막 글자에서 두 칸 띄우고 `끝.`을 쓴다.
- 원고에 `끝.`을 직접 쓰지 않는다. 엔진이 붙인다.

// ── 엔진 호출부: 엔진을 바꾸려면 이 함수만 교체한다 ──────────────────────────
async function render(md, docType, docMeta) {
  const warnings = []
  const gongmun = { preset: PRESET[docType] }
  if (docType === "gian" && docMeta) {
    const firstH1 = md.match(/^#\s+(.+)$/m)?.[1]?.trim()
    gongmun.docHead = { ...docMeta.head, title: docMeta.head?.title ?? firstH1 }
    gongmun.docFoot = docMeta.foot
  }
  if (Array.isArray(docMeta?.approval)) gongmun.approval = docMeta.approval
  const bytes = await markdownToHwpx(md, { gongmun, warnings })
  return { bytes: Buffer.from(bytes), warnings }
}

가.평가를 먼저 만드는 이유

Anthropic은 긴 지시문을 쓰기 전에 평가부터 만들라고 권합니다. 순서는 이렇습니다. 스킬 없이 모델에게 먼저 시켜 보고, 틀리거나 모자란 점을 기록하고, 그 빈틈을 메우는 만큼만 지시문을 씁니다. 그러면 상상 속 문제가 아니라 실제 문제를 푸는 스킬이 됩니다.

보고서 요약문에 경고가 뜸요약문 끝맺음 관행("~하고자 함.")이 규칙 파일에 없음report-rules.md와 템플릿 수정

고칠 때는 원인을 셋 중 하나로 가립니다. 지시가 모호했는지(SKILL.md·참고 문서 수정), 규칙이 빠졌는지(규칙 파일 수정), 스크립트가 틀렸는지(스크립트 수정). 고친 뒤에는 전체 사례를 다시 돌려 다른 곳이 나빠지지 않았는지 확인합니다. 모델이 실수할 때마다 그 교정을 SKILL.md의 "주의" 목록에 추가하는 것이 가장 직접적인 개선 방법입니다.

이전 대화에서 만든 skill-eval(rubric.json + score.mjs)은 결과물 평가를 스크립트로 채점하는 방식의 축소판입니다. 이 스킬의 evals.json과 함께 쓸 수 있습니다.

Ⅶ추가로 꼭 알아야 할 것

가.description이 켜짐의 전부다

모델은 목록의 description만 보고 스킬을 켤지 정합니다. 본문이 아무리 좋아도 description이 부실하면 스킬은 쓰이지 않습니다.

  1. 무엇을 하는지와 언제 쓰는지를 모두 적습니다.
  2. 사용자가 실제로 쓰는 말을 넣습니다. "품의", "결재 올릴 문서", "한글 파일", "hwp"처럼 사람들이 요청할 때 쓰는 표현입니다.
  3. 쓰지 않을 경우를 적어 경계를 긋습니다. 비슷한 스킬끼리 헷갈리지 않게 합니다.
  4. 3인칭으로 씁니다. "~한다. ~할 때 사용한다."처럼 쓰고, "제가 도와드릴게요" 같은 1인칭이나 "당신은 ~할 수 있습니다" 같은 2인칭은 쓰지 않습니다.
  5. 몇 문장으로 짧게 씁니다. 표준 한도는 1,024자이고, 모든 스킬의 description이 늘 컨텍스트에 올라가므로 길면 전체가 무거워집니다.
나쁜 예와 좋은 예
# 나쁜 예: 무엇을 하는지도, 언제 쓰는지도 알 수 없음
description: 문서 작성을 도와줍니다.

# 좋은 예: 무엇 + 언제(사용자 표현) + 쓰지 않을 때
description: 사내 기안문과 보고서를 한글(HWPX) 파일로 작성한다. 사용자가 기안, 품의, 결재 올릴 문서, 검토보고, 보고서, 한글 파일, hwp, hwpx를 언급하거나 메모·회의 내용을 정식 사내 문서로 만들어 달라고 할 때 사용한다. 워드·엑셀·PDF 작성이나 기존 한글 파일을 읽고 요약만 하는 요청에는 사용하지 않는다.

나.짧게 쓰되, 작은 모델에게는 예시로 구체화한다

  • 모델이 이미 아는 것은 뺍니다. 기안문이 무엇인지, 마크다운이 무엇인지 설명할 필요가 없습니다. 각 문장마다 "이 문장이 없으면 모델이 틀릴까?"를 물어 보고, 아니면 지웁니다.
  • SKILL.md 본문은 500줄 이하로 두고 긴 내용은 참고 파일로 뺍니다. 참고 파일은 SKILL.md에서 한 단계로만 연결합니다. 참고 파일이 또 다른 파일을 가리키게 하면 모델이 끝까지 따라가지 않을 수 있습니다.
  • 선택지를 늘어놓지 말고 기본값 하나와 예외를 줍니다.
  • 용어를 하나로 통일합니다. 이 스킬은 끝까지 "원고"라고만 부르고 초안·draft를 섞지 않았습니다.
  • 작은 로컬 모델은 더 구체적인 지시가 필요합니다. "짧게 써라"와 부딪히는 것처럼 보이지만, 설명 문장을 늘리기보다 예시·템플릿·스크립트를 늘리는 것으로 풀면 둘 다 지킬 수 있습니다.

다.보안: 스킬 설치는 프로그램 설치와 같다

스킬은 지시문과 코드로 모델의 행동을 바꿉니다. 악의적인 스킬은 겉으로 내세운 목적과 다르게 도구를 쓰도록 모델을 유도할 수 있습니다.

  • 직접 만들었거나 검토를 마친 스킬만 씁니다.
  • 스크립트뿐 아니라 SKILL.md와 참고 문서의 지시문도 코드처럼 감사합니다. 악성 지시는 글 속에 숨어 있을 수 있습니다.
  • 외부 URL에서 내용을 가져오는 스킬은 쓰지 않습니다. 가져온 내용에 악성 지시가 섞일 수 있고, 믿을 만한 스킬도 외부 의존성이 바뀌면 오염될 수 있습니다.
  • 실행기 권한을 최소로 둡니다. 우리 실행기처럼 셸 대신 허용 목록을 쓰고, 작업 폴더를 제한하고, 시간 제한을 둡니다.
  • 남이 만든 프로젝트 폴더를 받으면 그 안의 .agents/skills/에 스킬이 섞여 들어올 수 있습니다. 프로젝트 스킬은 신뢰를 확인한 뒤에만 불러오게 합니다.
  • 은행 적용: 스킬 등록 심사, 변경 시 코드 리뷰, 배포본 해시 기록, 도구 호출 감사 로그(우리 실행기의 logs/audit.jsonl).

라.운영과 관리

  • 머리말의 metadata에 담당 부서와 버전을 적고, 스킬 폴더를 Git으로 관리해 누가 무엇을 바꿨는지 남깁니다.
  • 짝을 이루는 파일(house-style.md와 house-rules.json)은 함께 고친다는 규칙을 정합니다.
  • 사내 배포 위치를 한 곳으로 정하고, 각 PC의 ~/.agents/skills/로 복사하는 방식으로 배포합니다.
  • 분기마다, 그리고 사내 모델을 바꿀 때마다 평가를 다시 돌립니다.

바.제품별 추가 기능은 표준 밖이다

Claude Code는 표준에 없는 필드를 더 지원합니다. 다른 제품에서는 무시될 수 있으므로, 스킬의 핵심 동작은 표준 필드만으로 되게 만들고 이런 필드는 편의 기능으로만 씁니다.

필드·문법뜻
disable-model-invocation: true사용자가 /이름으로 부를 때만 실행. 배포·발송처럼 부작용이 큰 작업에 사용
user-invocable: false모델만 켤 수 있고 / 메뉴에서 숨김. 배경지식용
allowed-tools스킬이 켜진 동안 확인 없이 쓸 도구
context: fork대화 기록 없이 별도 작업 공간(서브에이전트)에서 실행
$ARGUMENTS/이름 뒤에 붙인 인자를 본문에 끼워 넣음
!`명령`스킬을 넘기기 전에 명령을 실행해 그 결과를 본문에 끼워 넣음

사.한국어·윈도우·폐쇄망에서 챙길 것

  • 인코딩. 모든 파일은 UTF-8로 저장합니다. 윈도우 메모장이 붙이는 BOM 때문에 머리말을 못 읽는 실행기가 있습니다(우리 실행기는 BOM을 제거하고 읽습니다).
  • 경로. 윈도우에서도 경로는 scripts/check_draft.mjs처럼 슬래시로 적습니다.
  • 이름과 내용. 스킬 name은 영문 소문자로 짓는 것이 안전하고(Ⅴ장 다 1)), description과 본문은 한국어로 써도 됩니다. 사용자가 한국어로 요청하므로 description에 한국어 표현을 넣는 편이 잘 켜집니다.
  • 실행 중 다운로드 금지. npx, uvx처럼 그때그때 내려받는 명령은 폐쇄망에서 실패합니다. 의존성은 미리 설치해 반입합니다.
  • 버전 고정. 엔진과 의존성 버전을 고정하고, 올릴 때는 평가를 다시 돌린 뒤 올립니다.
